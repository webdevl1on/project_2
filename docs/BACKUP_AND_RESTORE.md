# Security 1.5 — резервні копії та відновлення

Реалізовано у `feature/security` поверх `ea7f6da` / Security 1.4. Перевірено також `origin/testing=00cf012`; гілку `testing` не змінено. PostgreSQL 17, поточний Alembic head **0009_access_control**. Нових ORM-таблиць, залежностей чи міграцій немає. Робочі БД, ключі, старі копії та системні планувальники під час реалізації не змінювалися.

## Що повторно використано

- `User`, `UserSession`, централізовані MFA/CSRF/Origin, системні ролі й п’ятихвилинне повторне підтвердження MFA.
- Чинні `DocumentStorage`, незмінні оригінали документів, логічне вилучення, приватна видача та `DocumentFile.storage_key/size/sha256`.
- `Settings` для явного середовища й окремих сховищ, Alembic/schema checker, `database_lease` для міжпроцесного блокування.
- `cryptography` для AES-256-GCM, HKDF та вже наявна MFA-перевірка відповідності ключів БД.

Попередні SQLite backup перед міграціями й ручні `pg_dump` не забезпечували автоматичної зашифрованої узгодженої копії PostgreSQL разом із файлами. Цей модуль їх не запускає й не видаляє їхні результати.

## Потік та узгодженість

`routers/backups.py → services/backups/commands.py → BackupEngine → BackupRepository → PostgreSQL/pg_dump`. Вебзапит лише записує підписане завдання; дані копіює серверний worker, який запускає системний планувальник.

1. Worker бере OS lease свого середовища та PostgreSQL advisory lease поточної схеми. Другий backup відхиляється, зокрема з іншого процесу.
2. Спільний PostgreSQL snapshot gate підключено до `service_transaction`, `StaffService.write_unit`, ORM flush і Session DML. Копіювання коротко бере винятковий gate, чекаючи завершення вже розпочатих записів.
3. У `REPEATABLE READ` експортується snapshot. Під цим gate закріплюються файли документів: hardlink незмінного оригіналу, або повна копія, якщо hardlink недоступний. Фото копіюються. `.pending-*` документів не включаються.
4. Gate звільняється; звичайні записи продовжуються. `pg_dump --snapshot` читає ту саму точку БД. У тому самому snapshot читаються кількості рядків, файлові посилання й перевіряються MFA-ключі.
5. Перевіряється кожне посилання `DocumentFile`, включно з логічно вилученими файлами, його розмір і SHA-256. Відсутній/змінений файл зриває backup. Зайві історичні оригінали теж зберігаються.
6. Створюються зашифровані архів і капсула конфігурації; повна автентифікація, розпакування та перевірка маніфесту передують публікації копії.

Читання не блокується. Спроба нового запису під час gate отримує **503 / Retry-After: 5**; дані не записуються частково. На іншому томі або великому каталозі фото пауза довша, оскільки потрібне фізичне копіювання. `freeze_seconds` включає очікування gate і закріплення файлів. Порядок блокувань у кадровій транзакції збережено: snapshot gate перед організаційним lock.

Гарантія узгодженості стосується записів через чинні компоненти застосунку. Прямий SQL, міграції та стороння зміна/видалення файлів не беруть цей gate; такі роботи потрібно окремо узгоджувати з worker. Модуль не копіює активний каталог даних PostgreSQL.

## Склад і захист

| Компонент | Вміст |
| --- | --- |
| `<id>.p2b` | AES-256-GCM: custom-format dump схеми, документи, фото, знімок захищеного операційного журналу та маніфест. |
| Маніфест усередині архіву | ID/тип/UTC snapshot, середовище й fingerprint джерела, release, Alembic revision, PostgreSQL major, кількості рядків, файлові посилання, розміри й SHA-256 кожного члена, hash капсули. |
| `<id>.p2s`, інший каталог та ключ | Окремо зашифровані `PROJECT2_MFA_KEYS`, `PROJECT2_MFA_CURRENT_KEY`, `STAFF_SIGNING_KEY`, WebAuthn RP ID/origins. Секрети не потрапляють у відкриті метадані/HTTP/логи. |
| Каталог, черга, плани й журнал | HMAC-SHA256 з ключем HKDF, атомарна заміна файлів. Журнал має підписані події, ланцюжок і кінцевий anchor в одному атомарному envelope. Автор — перевірений ID або NULL для запланованої серверної операції. |

Архіви не містять ключів свого шифрування. Ключі архіву та капсули мають бути різними; повторне використання будь-якого ключа між цими keyring відхиляється. Неправильний ключ, пошкодження, підміна маніфесту, небезпечний tar path/link або інша версія відхиляються до відновлення.

`release` задає оператор для незмінного артефакту застосунку, наприклад фактичний commit. Збережіть відповідний код, lock/requirements та інсталяційні пакети окремо: модуль не архівує Git/venv/ОС. Серверні ролі PostgreSQL, доступ до дисків, TLS-сертифікати та нові підключення при відновленні створює оператор; `--no-owner --no-privileges` не відновлює серверні PostgreSQL-паролі. Користувачі **застосунку**, паролі, ACL, фактори, історія й аудит входять у dump.

Staging містить **тимчасовий відкритий dump і файли**. Потрібен приватний зашифрований OS-том (BitLocker/LUKS), достатньо місця щонайменше для dump, tar, зашифрованого результату та перевірки, POSIX 0700/0600 або еквівалентні NTFS ACL. Звичайне завершення прибирає staging; після аварійного вимкнення залишки перевіряє й видаляє оператор при зупиненому worker. Захищене стирання SSD і захист від OS administrator, який уже має ключі, не заявляються.

Каталоги backup/капсул/staging/drill і результату recovery не можуть бути всередині `app/static`; небезпечна конфігурація відхиляється до запису. Для інших web-серверів оператор також повинен виключити ці каталоги з публічної видачі.

Журнал підписаний, але не є зовнішнім WORM: OS administrator із ключами може переписати його. Для незалежного контролю потрібні окремий захищений носій/моніторинг. Поточне обмеження envelope — 16 MiB; контролюйте розмір `operations.json`. До досягнення межі оператор має архівувати старий корінь разом із ключами та відкрити новий корінь резервування; старі копії й журнал не видаляються. Автоматичну ротацію журналу тут не реалізовано.

## Налаштування Windows

Усі наведені шляхи — приклади. Команди виконуються **вручну** з кореня репозиторію. Встановіть PostgreSQL **17** client tools та використовуйте вже створений персональний Master з MFA. Worker запускається під окремим OS-акаунтом, який читає джерела, працює з відповідною БД і має права лише на потрібні backup-каталоги.

1. Створіть приватні незалежні каталоги: основні копії (`PROJECT2_BACKUP_STORAGE`), капсули, staging, ключі, необов’язкові drills та зовнішній том. NTFS ACL залишають службовому акаунту й уповноваженим OS-адміністраторам; перевірте це для дочірніх файлів і мережевої папки. PowerShell-скрипти не змінюють ACL автоматично.
2. Створіть два ключі поза Git і поза всіма backup/source каталогами:

```powershell
.venv\Scripts\python.exe -m app.services.backup keygen --file C:\project2-secrets\backup-keys.json
.venv\Scripts\python.exe -m app.services.backup keygen --file C:\project2-secrets\recovery-keys.json
Copy-Item config\backup.example.json C:\project2-secrets\backup.json
```

`keygen` не перезаписує наявний файл. Замініть приклади в JSON: `release` — фактичний deployment commit, `tool_dir` — каталог PostgreSQL 17; узгодьте шляхи й місткість. `external: null` вимикає зовнішню репліку до її налаштування. Основний корінь береться з `PROJECT2_BACKUP_STORAGE`, а не з JSON.

3. У приватному `.env` для **саме цього** середовища задайте чинні DATABASE_URL, каталоги, MFA/signing/RP-конфігурацію й:

```dotenv
PROJECT2_BACKUP_CONFIG=C:/project2-secrets/backup.json
```

Браузерний процес і worker повинні отримувати однакову конфігурацію середовища/backup. Для ручного запуску:

```powershell
$env:PROJECT2_ENV_FILE = 'C:\project2-secrets\backup.env'
.venv\Scripts\python.exe -m app.services.backup create
.venv\Scripts\python.exe -m app.services.backup verify --id <ID_КОПІЇ>
.venv\Scripts\python.exe -m app.services.backup status
```

Ці команди запитують чинний персональний session token Master **прихованим prompt**, після свіжого повторного MFA на `/account/security`. Не передавайте cookie в аргументах, логах чи документації; вона залишається секретом. `status` через HTTP доступний також Admin. Для звичайної роботи використовуйте `/admin/backups`, без ручного перенесення cookie.

4. Перевірте один цикл worker, а потім зареєструйте Task Scheduler із PowerShell адміністратора:

```powershell
.\scripts\backup\Run-Backup.ps1 -BackupRepoRoot C:\project_2 -BackupPython C:\project_2\.venv\Scripts\python.exe -BackupEnvFile C:\project2-secrets\backup.env
$BackupCredential = Get-Credential
.\scripts\backup\Install-BackupTask.ps1 -BackupRepoRoot C:\project_2 -BackupPython C:\project_2\.venv\Scripts\python.exe -BackupEnvFile C:\project2-secrets\backup.env -BackupCredential $BackupCredential
```

Обліковий запис завдання повинен мати `Log on as a batch job` та доступ до мережевого сховища, якщо воно використовується. Існуюче завдання скрипт не замінює. Перевірте Task History, Last Run Result і доступ до томів **під цим акаунтом після виходу з Windows**. Скрипти PowerShell/реальний Task Scheduler у середовищі Codex не виконувалися.

## Планування, RPO та зберігання

Task Scheduler або `scripts/backup/project2-backup.timer` перевіряє чергу щохвилини; постійний браузер/вбудований scheduler у web-процесі не потрібний. За замовчуванням worker робить самодостатню точку **кожні 30 хвилин**, а після 02:00 **UTC** — щоденну `full`. `checkpoint` теж містить повний dump і всі файли; це не інкрементальний/WAL backup. Інтервал конфігурується в межах 1–60 хвилин. Пропущені запуски не домальовуються заднім числом.

Linux: після перевірки шляхів і OS-акаунта у `.service` вручну встановіть файли до `/etc/systemd/system/`, створіть приватний `/etc/project2/backup.env`, виконайте `systemctl daemon-reload` та `systemctl enable --now project2-backup.timer`. Це не виконується застосунком. Для запуску `.service` потрібні записувані каталоги поза захищеною частиною `/etc`/`/usr`; `PrivateTmp=true` врахуйте при виборі staging.

RPO ≤1 година потребує успішного завершення перевірених точок з інтервалом snapshot ≤3600 с, достатньої швидкості dump/диска/реплікації та моніторингу. Якщо цикл триватиме понад бюджет або є помилки, частота планувальника сама по собі RPO не забезпечить. Статус показує прострочення локальної та зовнішньої копії. Для катастрофи основного майданчика рахувати потрібно вік **зовнішньої** копії.

Помилка створює підписаний `alert.json`, подію журналу та ненульовий exit code worker. Можна налаштувати `alert_command` як довірений список executable/args: він отримує безпечний JSON через stdin, без shell і секретів. Реальний канал сповіщення та контроль відсутності запусків налаштовує адміністратор. Без зовнішнього моніторингу вимкнений сервер не може повідомити про власну відсутність.

`prune=false` за замовчуванням. При явному `prune=true` retention стосується тільки підписаних записів, створених цим модулем: `full_days=14`, `checkpoint_hours=48`. Перед видаленням давніх копій повторно перевіряються дві новіші локальні й, якщо налаштовано, зовнішні копії. Пошкодження новішої копії блокує очищення. Останні дві підтверджені точки зберігаються; невідомі старі backup-файли не видаляються. Автоматично retention у цій роботі не застосовувався до наявних даних.

`max_bytes` — бюджет основного кореня й капсул, включно з метаданими, за замовчуванням 100 GiB. Перевищення відхиляє нову копію; стару не підміняє. Місце staging і зовнішнього тому контролюється окремо. Якщо місце вже вичерпано, потрібне рішення оператора; система не видаляє останню працездатну точку заради нового backup.

## Зовнішнє сховище

Підтримано окремий змонтований каталог/UNC на іншому захищеному носії; файловий транспорт забезпечує ОС. Після ручної перевірки правильного тому створіть у ньому `.project2-backup-volume` зі значенням `external_marker` з конфігурації. Відсутній/чужий marker зриває реплікацію, щоб відмонтований диск не підмінявся випадковою папкою. Symlink-сховище заборонене.

Worker копіює вже зашифровані `.p2b` та `.p2s` (останні — у підкаталог `secrets`), перевіряє їх і лише потім публікує підписаний каталог зовнішньої копії. Ключів на цьому томі немає. Недоступність зовнішнього сховища фіксується як помилка, але добра локальна копія зберігається. Відновлення зовнішньої копії використовує `--external` і знову перевіряє весь комплект. Об’єктний S3 API/хмарні credentials, WORM та географічну незалежність носія цей модуль не налаштовує.

## Ключі, escrow та ротація

- Окремо збережіть обидва backup keyring, всі потрібні покоління MFA-ключів та відповідний deployment/env у захищеному escrow, доступному при втраті основного сервера. Перевірте відновлення escrow; резервна капсула сама себе розшифрувати не може.
- Після перезапуску використовуються ті самі файли ключів. Немає генерації випадкового ключа при старті. Відсутній/неправильний ключ закриває операцію.
- Ротація: призупинити worker, зберегти escrow старого keyring, додати новий випадковий 32-байтний base64 ключ з новим ID до `keys`, змінити `current`, атомарно замінити приватний JSON; повторити окремо для ключа капсул. Старі ключі **залишити**, доки потрібні старі архіви, HMAC-метадані та журнали. Перевірити стару і нову копію та ізольоване відновлення, відновити scheduler. Не генерувати ключ у Git/консолі/логах.
- Зміна MFA-ключів — окрема чинна процедура [SECURITY.md](SECURITY.md). Цей модуль їх не обертає й не переписує. `check_mfa` перевіряє marker та всі зашифровані TOTP/незавершені MFA-секрети.

## Адміністративний інтерфейс

`/admin → Резервне копіювання → /admin/backups`: останній успіх/помилка, наступний UTC запуск, тип/розмір/перевірка копій, зовнішній том, останній drill, черга та операційний журнал.

| Дія | Право |
| --- | --- |
| Стан/список без секретів і без вмісту документів | Персональна MFA-сесія Master або Admin. |
| Ручний запуск / перевірка | Master та свіжа MFA, чинні CSRF/Origin. Worker повторно перевіряє активність/роль і давність запиту ≤5 хв. |
| Відновлення / дозвіл регулярного drill | Захищена серверна CLI-процедура Master; HTTP restore/download немає. |
| User, включно з делегованим адміністратором матриць | Доступу до цього розділу й архівів немає. |

Роль Master не відкриває персональні документи через API: резервування — окрема системна операція. Не додано нових ACL-галочок, спільних користувачів чи bypass. Polling статусу не поновлює 15-хвилинний idle timeout.

## Ізольоване відновлення

Підтримується лише **нова порожня БД** `project2_restore_<8–32 hex>` на PostgreSQL 17. Джерело, `project2_dev`, `project2_prod`, непорожня ціль і source-каталоги відхиляються. Для цілі потрібна роль-власник та `btree_gist`/право його встановлення; superuser застосунку не потрібний. URL задається приватною змінною середовища, не аргументом:

```powershell
# Значення URL із паролем задайте через захищений env-файл або сховище секретів.
# PROJECT2_RESTORE_DATABASE_URL -> нова порожня project2_restore_<hex> на окремому сервері.
.venv\Scripts\python.exe -m app.services.backup restore-plan --id <ID_КОПІЇ> --reason 'Ізольована перевірка відновлення'
.venv\Scripts\python.exe -m app.services.backup restore-apply --plan <ID_ПЛАНУ> --output C:\project2-isolated\recovered --confirm --write-config C:\project2-secrets\restored-critical.json
```

Перед `--confirm` прочитайте plan: snapshot/версія/ревізія, ціль, кількості рядків. План підписаний, прив’язаний до користувача, target fingerprint/SSL-параметрів, hashes обох файлів і діє 30 хв. Повторне застосування заборонено. Ціль серіалізується OS lease та PostgreSQL lease навіть при різних source-коренях.

`pg_restore --single-transaction --exit-on-error` без `--clean`; потім schema checker, точні row counts, файлові посилання/SHA-256 і MFA-ключі. Старі bearer-сесії та незавершені MFA flows видаляються **тільки в копії**, щоб їх не можна було використати після відновлення. Фактори, паролі, користувачі, ACL та історія залишаються. Це навмисна інвалідація відновлених сесій, а не втрата авторів аудиту.

Файли публікуються в новий каталог лише після перевірок. У ньому `documents`, `photos`, підписаний `recovery.json`, знімок попереднього операційного журналу й зашифрована `critical-config.p2s`. `--write-config` після підтвердження Master може окремо записати приватний JSON секретів **поза Git**; не додавайте його до звітів. При невдачі ціль залишається ізольованою для аналізу, план витрачений; автоматичного перезапису/перемикання основного середовища немає. Повтор — нова порожня ціль і новий plan.

Для запуску перевіреної копії використовуйте окремий env: `PROJECT2_ENV=testing`, URL цієї `project2_restore_<hex>`, відновлені `documents/photos`, незалежні temporary/export/backup каталоги, секрети з відповідної капсули. Це вузьке додаткове допустиме ім’я у Settings; PostgreSQL pytest як і раніше дозволений **лише у project2_ci**. Для непублічної схеми з `recovery.json` оператор налаштовує search_path ролі; типовий deployment використовує public. WebAuthn потребує збережених RP/origin або окремої погодженої зміни конфігурації; пароль/TOTP/резервний код перевіряються чинними сервісами.

### Втрата основного сервера

До обох restore-команд додайте `--offline-master`. Потрібен локальний OS administrator; після відновлення БД, до публікації файлів, CLI перевірить **справжній пароль відновленого Master та його TOTP або одноразовий резервний код**. Службовий акаунт чи universal token не використовуються. Правильність цих факторів перевіряє існуючий MFA-сервіс; ID Master потрапляє у recovery report. Без доказу файли не публікуються.

Заздалегідь збережіть резервні коди Master окремо від backup-ключів. Якщо втрачено всі фактори/коди Master, стандартний offline restore не обходить MFA: потрібна окрема захищена процедура [recover_master_mfa](SECURITY.md), локальна перевірка особи та ручний супровід ізольованої копії. Автоматичного обходу цієї ситуації не додано.

### Повернення робочої системи

Гаряче перезаписування production не підтримується. Спочатку перевіряється ізольована копія. Далі — окреме вікно обслуговування оператором: припинити вхідний трафік і worker/записи, зберегти стару БД та каталоги як rollback-комплект, підготувати нову **окрему** production-інсталяцію з правильними іменами/ролями/файлами/ключами, виконати schema/MFA/файлові та прикладні smoke-перевірки і лише потім перемкнути трафік. Не перейменовуйте тестову БД й не міняйте два storage-каталоги на живому сервері частинами. При невдачі до відкриття трафіку поверніть цілий попередній комплект. Ці робочі дії не виконуються HTTP або автоматично цим модулем.

## Регулярне тестове відновлення

Окремий ізольований PostgreSQL cluster повинен мати `project2_ci`; його drill-роль має право створювати й видаляти **власні** тимчасові БД. Це не роль вебзастосунку й не prod server. Задайте URL у приватній `PROJECT2_BACKUP_DRILL_DATABASE_URL`, `drill_root` — приватний каталог.

```powershell
.venv\Scripts\python.exe -m app.services.backup approve-drill --reason 'Щотижневий контроль на ізольованому CI' --days 30 --confirm
.venv\Scripts\python.exe -m app.services.backup drill
# Дострокове відкликання дозволу:
.venv\Scripts\python.exe -m app.services.backup revoke-drill
```

Master підтверджує свіжу MFA; permit підписаний, діє максимум 30 днів, прив’язаний до конкретного CI URL/fingerprint. Роль/активність Master перевіряються при кожному виконанні. Worker за замовчуванням робить drill раз на 168 годин. Створюється випадкова `project2_restore_<hex>`, виконується реальний restore і вимірювання; потім видаляються **лише створені цим викликом** БД та тимчасові файли. `project2_ci` не очищується. Після аварії залишок випадкової цілі розбирає оператор. Прострочений permit потребує нового підтвердження; це не постійний bypass Master.

RPO ≤1 година та RTO ≤4 години залишаються **цілями**, а не підтвердженим SLA. Не виконано годинного виробничого спостереження, великого production benchmark, Windows Task Scheduler, перевірки реального зовнішнього/віддаленого тому чи production cutover. За межами етапу: WAL/PITR, інкрементальні копії, S3 API, автоматичний failover/production overwrite, керування зовнішнім KMS/WORM і автоматична ротація операційного журналу.
