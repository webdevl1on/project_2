# Планування, завершення та контроль подій

## Що використано, що додано

Наявні PersonEvent, EventType/EventSubtype, PersonEventService, EventRepository, спільний Modal та /events розширені. Персональне володіння подією, точні Date, кадрова дата Europe/Kyiv, HTTP URL і механізми транзакцій збережені. Штатна посада не стає власником події.

Нові можливості: орієнтовне завершення, явне підтвердження фактичного завершення, майбутні плани, розрахункова служба, незалежний контроль строків, навігація місяцями, зміна ширини ПІБ, додаткові штатні колонки, дворядкові тип/підтип і відтінки.

## Дані й переходи

PersonEvent має два нові поля: `planned_end Date NULL` і `completion_confirmed Boolean NOT NULL DEFAULT false`. Наявні `date_start`, `date_end`, `duration` збережені. Планова тривалість — вхідний параметр, який обчислює тільки planned_end; не дублюється в БД. Усі дати повні календарні, без підстановки сьогодні або відсутніх компонентів. HistoryModel, системний UTC та механізм неповних дат не змінювалися.

- Початок обов'язковий. Планове завершення не раніше початку.
- Фактичне завершення лишається NULL до явної дії. Прапорець підтвердження потребує фактичної дати; майбутню фактичну дату підтвердити не можна. Фактична duration рахується включно й не є плановою.
- У новій формі фактична дата/тривалість без прапорця не приймаються. Наявні сервісні/HTTP-виклики, що явно передають date_end або фактичну duration без нового параметра, зберігають попередній контракт явного введення фактичного завершення. Неявного завершення відпустки від цього не відбувається.
- Дія «Підтвердити завершення / повернення» відкриває той самий редактор. Підставляє планову дату лише якщо вона вже настала; діловод може змінити її, перевірити й натиснути збереження. Початковий planned_end зберігається.
- Автоматично завершити попередню відкриту подію дозволено лише для SERVICE, DUTY, DAY_OFF, при створенні нової фактичної події, за попередніми перевірками всіх конфліктів. VACATION, HOSPITAL, BUSINESS_TRIP та невідомі типи потребують підтвердження. Редагування не завершує чужих записів.

Міраж події визначається динамічно: date_start пізніше кадрового сьогодні. Окремого EventType або таблиці міражів немає. Це не PersonPositionMirage, який не змінено. План може співіснувати з фактичною відкритою подією, не змінюючи її. Два плани перевіряються за їхніми плановими межами (без відомого завершення інтервал відкритий). Коли початок настав, мітка міражу зникає; невирішене накладання відображається як конфлікт, без прихованого закриття історії. Плани з фактичною датою завершення в майбутньому новими записами не приймаються.

## Стан на дату

Єдиний `event_views.state_on` використовується журналом і штаткою:

1. Вакантна штатна посада позначається окремо.
2. Кілька подій або нова подія разом із непідтвердженим попереднім завершенням — конфлікт.
3. Орієнтовний строк минув, завершення не підтверджене — «Потребує підтвердження завершення».
4. За поточної події відображається її тип/підтип.
5. За відсутності поточної й невирішеної попередньої — розрахункова «Служба» (`__base__`). Вона відрізняється від реально внесеної SERVICE в підказці та підсумках, не підтверджує фізичної присутності й не створює рядків БД.

Підсумки рахують кожен день один раз незалежно від масштабу. Пунктир/штрихування позначають майбутні плани. Назва типу й підтипу, повні періоди та планові строки доступні текстом і в tooltip. Безпечні значення EventType.event_color використовуються як основа кольору; підтипи отримують різні світлі відтінки. Старі DUTY/DAY_OFF та їхня історія не переміщуються. Для SERVICE додано підтипи SERVICE_DUTY, SERVICE_AFTER_DUTY, SERVICE_DAY_OFF; діють звичайні активність і належність довідників.

## Проблеми діловода

`event_rules.problem` — незалежна від HTML розрахункова функція; `event_views.problems` читає непідтверджені події, імена й формує `/events/problems`. Ідентичність `event:<event_id>`: максимум один пункт на подію, повторне читання нічого не записує. Зміна строку перераховує список, підтвердження прибирає проблему, але не видаляє подію та її планові реквізити.

| Правило | Момент появи |
| --- | --- |
| BUSINESS_TRIP / BUSINESS_TRIP_MISSION (СБЗ) | За 20 календарних днів до planned_end, включно; після planned_end — прострочено. |
| VACATION | Наступного дня після planned_end без підтвердження. |
| HOSPITAL | На 16-й календарний день включно від початку. |
| VLK або підтип VLK/HOSPITAL_VLK, якщо вони існують | На 16-й день; без змін медичної довідки. |
| Інша подія з відомим planned_end | Строк уже минув, завершення не підтверджене; додаткових попередніх порогів немає. |

Групи: «Ротації / СБЗ», «Відпустки», «Лікарняні», «ВЛК», «Інші події». Майбутні та підтверджено завершені записи не створюють проблем. Проблема не зникає через сам плин часу. Ручна зміна плану та підтвердження зберігаються в PersonEvent і захищені expected_state.

Чинний seed-довідник не має типу/підтипу ВЛК. Екран повідомляє про це. Медичні довідники автоматично не доповнюються; для реального ввімкнення ВЛК-контролю потрібне погоджене доповнення саме довідника подій. Адміністративний редактор правил/порогів не створений; 20/15 поки константи.

PersonnelTask, Injury, MedicalExam, Award не використовуються цим контролем, FK до них не додано. Закриття медичної проблеми не змінює подію; підтвердження події не змінює медичні завдання чи придатність.

## Інтерфейс журналу

`journal_controls.js` керує лише місячною навігацією та локальним виглядом журналу. Стрілки/вибір місяця й року встановлюють точні перший/останній дні, зберігаючи ручний діапазон, GET-фільтри, сортування й масштаб. Дати періоду, редактора та карток показані ДД.ММ.РРРР спільним ProfileDates; canonical/API залишаються ISO.

ПІБ змінює ширину правою межею (100–600 px; також стрілками клавіатури на розділювачі), обрізається з повним tooltip. № рядка, № посади та коротка посада вмикаються окремо. Номер рядка відповідає відфільтрованому/відсортованому списку. Штатні поля читаються з офіційного призначення на кінець діапазону; для непризначених вони порожні, при переході між посадами береться історична посада на цю дату. Перелік підрозділів охоплює весь період.

Налаштування ізольовані ключем `project2:event-journal:layout:v1`, не змінюють пресети штатки. Прокрутка вертикальна/горизонтальна, заголовки й ПІБ закріплені. Пагінації немає. Копіювання/призначення/Міражі/Undo штатки використовують попередні механізми.

## Міграція PostgreSQL

Ревізія планування `0002_event_completion` після `0001_postgresql`; поточний head — `0003_event_corrections`, див. [EVENT_CORRECTIONS.md](EVENT_CORRECTIONS.md). Лише Alembic; startup перевіряє head, не мігрує БД. Додаються два поля й CHECK: план не раніше початку, підтвердження потребує фактичного завершення. Дати/тривалість старих записів не змінюються. Старі завершені записи, дата завершення яких уже настала за Europe/Kyiv, визнаються завершеними за попереднім контрактом. Відкриті й старі майбутні фактичні завершення не підтверджуються автоматично. Останні зберігаються як є, редактор попереджає: діловоду слід явно перевірити/перенести строк у планове поле. Міграція не вгадує початковий намір.

SERVICE-підтипи додаються лише відсутні, без перезапису назв/активності та без перенесення історичних DUTY/DAY_OFF. На новій порожній БД їх додає чинний seed-процес. Повторний upgrade head — no-op. Downgrade із втратою рішень заборонений; для відновлення використовувати перевірений backup в окрему БД.

Окремий запуск у PowerShell **після перевірки DATABASE_URL, резервної копії та зупинки застосунку**:

```powershell
# Чинні PROJECT2_ENV/DATABASE_URL мають вказувати саме на потрібну БД.
$pgUrl = $env:DATABASE_URL -replace '^postgresql\+psycopg:', 'postgresql:'
pg_dump --format=custom --file=before_event_completion.dump $pgUrl
if ($LASTEXITCODE -ne 0) { throw 'Backup failed' }
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
```

Reset і повторне засівання людей не потрібні. На Linux еквівалентна команда після backup — `.venv/bin/python -m alembic upgrade head`. Робочі БД цим завданням не мігрувалися; перевірки лише на випадкових схемах project2_ci та тимчасових SQLite legacy-тестів.
