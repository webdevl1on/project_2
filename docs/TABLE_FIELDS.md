# Каталог полів таблиць

Джерело визначень — `app/table_fields.py`; склад `/person-positions` — `app/table_columns.py`. Каталог містить **55 інформаційних полів**. «№» і форма призначення — дві окремі службові колонки. Нові поля типово приховані, попередні 12 видимих колонок і їхні стабільні ключі збережено.

## Моделі та правила вибору

| Модель | Використання |
| --- | --- |
| `Position` | Рядок посади конкретної StaffVersion, усі предметні реквізити й відмінкові форми; номер унікальний у межах версії. |
| `PersonAssignment` | Вибране на as_of дату історичне призначення в межах StaffVersion; технічні FK не є інформаційними колонками. PersonPosition — тільки застарілий alias. |
| `Person` | РНОКПП та три канонічні компоненти народження. |
| `PersonName` | ПІБ, латинські варіанти й системні поля вибраного запису. |
| `PersonRank` → `Rank` | Вибраний запис звання, його наказ і саме його довідникове звання з усіма відмінками. |
| `Passport` | Реквізити, дві дати й системні поля вибраного паспорта. |
| `PersonServiceHistory` | Реквізити, дві дати й системні поля вибраної служби; не підмінює штатне призначення. |
| `HistoryModel` | Абстрактний клас: точні автоматичні `created_at`, `updated_at`, ознака `is_active`. |
| `PartialDateMixin` | Компоненти/проєкції дат, не окрема таблиця. |
| `PersonEvent`, `EventType`, `EventSubtype` | Перевірено структуру; за уточненням користувача залишені поза каталогом та інтеграцією цього етапу. |

Погоджене правило для **кожної** з чотирьох історичних моделей: один запис загалом → показувати його незалежно від активності; кілька записів → показувати єдиний активний; немає записів → `-`; кілька записів без активного або з кількома активними → `-` і попередження над таблицею. Ніякого вибору за created_at або зміни записів у БД. Усі реквізити одного виду беруться з одного вибраного запису.

`history_selection` у `app/repositories/person_repository.py` групує записи за person_id та повертає максимум один chosen_id; outerjoin зберігає вакансії, не множить посади. Відсутність relationship для паспортів не компенсується зміною ORM: використано наявний FK. Для решти моделей використано ті самі FK, що визначають relationships. Список вибору людини використовує таке саме правило ПІБ і не дублює людину.

## Поля за групами

Позначка nullable нижче описує **колонку джерела**, а не обов’язковість даних у рядку посади: пов’язаного запису може не бути навіть для NOT NULL атрибута. Компоненти предметної дати — одне логічне поле; сумісні Date-проєкції не дублюються. Для обчислюваного ПІБ nullable позначає можливість відсутнього результату.

## Фільтри, дати й отримання значень

- 41 скалярне поле мають каскадний multiple-select: 36 текстових, цілий номер посади, чотири булеві ознаки. Порожнє значення — чинний `__empty__`, булеві значення URL — `0`/`1`, підписи «Ні»/«Так». РНОКПП, коди й номери документів/наказів залишаються текстом, з початковими нулями.
- Шість предметних дат використовують чинні DateBinding/DateFilter, possible match, діапазони, неповноту й незалежні пріоритети компонентів. Відсутній запис не збігається з невідомою датою існуючого запису. Відсутні дані та всі NULL компоненти в таблиці показуються як `-`; частково відомі — через спільний форматтер з `_`.
- Вісім системних DateTime сортуються за точним SQL DateTime і показуються з часом, мікросекундами та UTC. Фільтр предметних дат до них не підключений: фільтрація системного часу поки не реалізована.
- Усі 55 полів мають однорівневе SQL-сортування за власним типом; ПІБ — окреме SQLAlchemy-вираження, узгоджене з серверним складанням назви. Ключі стабілізації порядку рядків: position_number, position_id. У неповних дат незмінна політика точні → часткові → невідомі.
- Всі моделі й атрибути явно перелічені серверним каталогом; запит ніколи не визначає модель, JOIN або ім’я атрибута. Метадані UI не передають SQL до клієнта. Сервіс допускає лише поля поточної конфігурації таблиці.
- Значення/форматування обчислюються на сервері в `row["values"]`. Jinja лише обходить конфігурацію та відображає значення; окрема форма призначення збережена.
- Без активних колонкових фільтрів результат і всі списки варіантів потребують одного SQL-запиту; за N активних фільтрів — 1+N (для кожного активного фільтра варіанти обчислюються без нього). Окремий запит завантажує людей для форм. Немає lazy-звернень до relationships чи запитів на кожен рядок. Це перевірено лічильником SQL для різної кількості людей.

## Підключення майбутньої таблиці

`table_configuration(table_id, selections, overrides=...)` приймає впорядковані пари група/перелік ключів з FIELDS. Перевизначення дозволені для української назви, типової видимості та розмірів. Конфігурація створює незалежні словники; повторні ключі та невідомі поля відхиляються. Самі визначення TableField повторно використовуються в різних таблицях.

Для нової сторінки потрібні явна серверна вибірка потрібних моделей і словники рядків за source, виклик field.display для вибраних полів, спільний Jinja/Checkbox Tree та наявні JS/CSS. Каталог не створює довільних JOIN автоматично: правила вибору історії залишаються відповідальністю сервісу конкретної таблиці. UI не потребує окремої гілки для нового предметного поля.

Існуючі пресети version 1, стан/ширини version 2 та історія не змінюють формату. Додавання полів не робить старі ключі застарілими: нові поля залишаються невидимими у старому пресеті, оригінал пресету не перезаписується. Приховування нового поля вилучає його фактичний URL-фільтр і filter_order так само, як для попередніх полів; undo відновлює стан.

## Свідомі межі

Первинні/зовнішні ключі не додано як предметні колонки. Компоненти дат представлені логічними датами, а похідні Date-проєкції не показуються окремо. Орган/посадова особа видачі наказу про звання, підстава служби, додаткові документи не оголошені: відповідних предметних атрибутів у поточних моделях немає. Не створено даних або колонок SQLite заради відображення.

Події/підподії відкладено за уточненням користувача. Повна історія не агрегується в рядок посади; наявні сторінки історії залишаються окремими. Правило вибору реалізоване для цієї таблиці й її списку призначення; сторонні сторінки та сервіси зміни історії не переписувалися. Вони досі можуть користуватися попереднім правилом is_active/.first().

Навантажувального тесту великих баз немає. Сервіс отримує всі результати без нової пагінації, варіанти фільтрів рахує в пам’яті. Адаптер неповних дат лишається SQLite. Перевірено Chromium; інших браузерів цей етап не охоплює.

Версії штатів та періоди призначень описані в [STAFF_HISTORY.md](STAFF_HISTORY.md). Нові системні поля/revision і технічний FK версії не додавалися до існуючих 55 інформаційних колонок; стабільні ключі збережено.

Поле Person.sex і нові словники/персональні відмінки ПІБ наразі обслуговують форми осіб та /admin, не додаються до каталогу штатної таблиці. Залишаються чинні 55 полів, порядок ключів і налаштування таблиці. Деталі — [NAME_CASES.md](NAME_CASES.md).

## Computed адреса та нові кадрові реквізити

full_address («Повна адреса реєстрації») — нове необов’язкове text-поле групи особистих даних, scalar-subquery активної registration PersonAddress через formatted_address, nullable/приховане типово. Зберігаються ті самі текстові знімки; окремого поля/summary адреси в БД немає. Усі text-поля підтримують серверний <key>__contains з NFC/casefold. Приховування та історія пов’язують його з базовою колонкою через column_keys. Накази PersonAssignment показуються/редагуються в спільних кадрових controls, жетон — в огляді та обліковому блоці; незалежні end_* / note / revision обслуговують хронологію й поки не додані окремими колонками. Див. [SERVICE_CHRONOLOGY.md](SERVICE_CHRONOLOGY.md).
