# Журнал подій і стан у штатці

Два окремі представлення, узгоджені з графічними референсами:

- `/events` — журнал за період: матриця людей і календарних інтервалів, права панель, події й підсумки.
- `/person-positions` — звичайна штатка з **однією** додатковою колонкою `event_on_date` на дату «Стан на дату». Історія не розгортається в кілька штатних рядків.

## Джерела та межі

PersonEvent — єдине джерело подій; PersonAssignment — джерело офіційних посад/підрозділів. Записів «поточної наявності» не створено. Читання не завершує відкриті події, не змінює тривалість і не записує сьогоднішню дату. «Служба» показується лише за реальною подією SERVICE, а не через факт призначення.

- «Немає події» — немає запису на цей день; це не доказ фізичної наявності.
- «вакантна» — штатна посада не має офіційного призначення на вибрану дату. До персонального журналу вакансії не додаються.
- «Кілька подій» — суперечливі історичні записи на одному дні. Довільний запис не обирається; підсумок рахує цей день один раз у категорії конфлікту.

Непризначені люди збережені в журналі, включно з їхніми незалежними подіями. Підрозділи рядка беруться з призначень, які перетинають період; при переведенні показується перелік фактичних підрозділів, а без таких призначень — «Без штатного призначення». ПІБ і звання використовують чинний однозначний вибір історії; невідомі значення не вигадуються.

## Журнал

Період містить обидві межі, не більше 366 днів. За замовчуванням — останні 14 днів до поточної кадрової дати Europe/Kyiv. Доступні масштаби день, календарний тиждень, місяць; крайні неповні тижні/місяці обмежені фактичним періодом.

Для тижня/місяця комірка показує кількість станів або кількість днів одного стану; tooltip розкриває всі підсумки. Це агрегація представлення, а не створення/об'єднання PersonEvent. Підсумки завжди рахують календарні дні й не збільшуються через зміну масштабу. Невідомі дні показані окремо, не як «Інше» чи «служба».

Фільтри: підрозділ, тип події, Unicode-пошук за ПІБ. Фільтр типу відбирає людей, у яких цей тип є у періоді; **решта їхніх подій залишається видимою**, що зазначено в інтерфейсі. Сортування ПІБ/підрозділу, напряму та фільтри зберігаються в URL. Вибір людини оновлює person_id без створення зайвих кроків browser history. Перехід між періодами використовує звичайні GET-навігації, тому браузерні Back/Forward збережені.

Вибір рядка/комірки відкриває праву панель. Вкладки «Події» та «Картка наявності», попередня/наступна людина, редагування й додавання працюють. Кнопки використовують чинний PersonEvents Modal та API, описані в [PERSON_EVENTS.md](PERSON_EVENTS.md). Нового write-сервісу, редактора довідників або видалення історії немає. Після успішного збереження журнал перечитує дані без навігації, з урахуванням поточних фільтрів.

CSV-експорт завантажує фактичну відфільтровану матрицю: ПІБ, підрозділ і повні описи комірок. UTF-8 BOM, роздільник `;`, лапки/перенесення рядків екрановані; рядки, схожі на Excel-формули, захищені текстовим префіксом. Серверні файли експорту не створюються.

## Штатка

`event_on_date` — обчислюване інформаційне поле каталогу, типово видиме, останнє після призначення. Його можна приховати/переставити, змінити ширину, включити до пресету й копіювати чинним механізмом. Окреме SQL-сортування/фільтр цієї колонки не додано: це відображення стану на контекстну дату, а не нове фізичне поле людини. Фільтр типів подій є в журналі.

«Компактний вигляд» явно застосовує через чинний ColumnController вісім колонок із референсу: №, номер посади, підрозділ, коротка посада, звання, ПІБ, призначення, подія. Компактний набір не застосовується автоматично до збереженого користувацького вигляду; іменовані пресети не змінюються. Зміна набору бере участь у чинній історії вигляду. Ширини зберігаються, як і раніше, окремо від пресетів.

Швидкі фільтри підрозділу/звання використовують старі URL-параметри та filter_order; решта параметрів зберігається. Багатозначні чинні фільтри показують «Кілька значень». Після редагування події оновлюється відповідний значок на поточну дату, без заміни рядків/форм чи втрати чернетки призначення. Самі призначення, Міражі, кадрові дати й нумерація не змінені.

## Карта модулів

| Модуль | Відповідальність |
| --- | --- |
| `app/event_display.py` | Спільні короткі назви, палітра, значки й легенда; це метадані UI, а не довідник кадрових фактів. |
| `repositories/event_repository.py` | Bulk-вибірка подій із типами/підтипами й підрозділів призначень, без commit. |
| `services/event_views.py` | Валідація періоду, денна проєкція, підсумки, масштаби, відбір/сортування людей, стан на дату. |
| `routers/event_journal.py` | GET `/events`, `/events/data`, `/events/presence?person_id=...&on=YYYY-MM-DD`; без ORM у роутері, відповіді no-store. |
| `table_fields.py`, `table_columns.py` | Одне поле/група події, його можливості й початкове розташування. |
| `service_person_positions.py` | Один додатковий bulk-запит подій для всіх показаних людей; без N+1 і множення рядків. |
| `components/event_badge.html`, `event_icons.html` | Спільні серверні значки/легенда та SVG-символи. |
| `static/js/event_ui.js` | Безпечний DOM значка, CSV-екранування/завантаження. |
| `event_journal.html`, `static/js/event_journal.js` | Матриця, права панель, фільтри/навігація й оновлення після запису. |
| `static/js/staff_event_presence.js` | Явний компактний вигляд, швидкі старі фільтри та оновлення значка. |
| `static/js/person_events.js` | Спільний `PersonEvents.open(id,label,{eventId,create})` і повідомлення `person-events:saved`; старі кнопки працюють. |
| `static/css/event_views.css` | Спільна палітра двох екранів, адаптивна матриця/панель, компактні картки. |

`profile_dates.js` підтримує необов'язковий `data-date-scope` на script: журнал маскує лише поля свого періоду, залишаючи ISO у canonical inputs. За відсутності цього атрибута чинна поведінка анкети не змінена. Дати PersonEvent, системні UTC-позначки й незалежні неповні предметні дати збережені.

## Обмеження та перевірки

Схема БД й Alembic не змінювалися; reset/міграції робочих БД не виконувалися. Нової системи доступу не додано: read views мають чинну політику кадрових/staff-сторінок, тому загальні production-прогалини авторизації з POSTGRESQL_SETUP залишаються.

Матриця завантажує всіх людей, які відповідають фільтрам, без вигаданої пагінації. Для дуже великих наборів може знадобитися окремий етап серверної пагінації/віртуалізації. Поточне обмеження періоду — 366 днів; це не обмежує довжину історії PersonEvent у БД.

Тести: `test_event_views.py`, доповнення PostgreSQL `test_person_events.py`, `browser/journal.cjs`, `js/event_ui.test.cjs`, регресія каталогу/колонок, дат і штатних операцій. Результати запусків наведені в CURRENT_STATE.
