# Контакти та повна анкета

## Модель і правила

`PersonContact` → `person_contacts`: id, person_id FK, contact_type phone/email, value (оригінал без крайових пробілів), normalized_value, label, note, is_primary, is_active, UTC created_at/updated_at та revision з чинного SystemTimestamps. Полів контактів у Person немає. Кількість записів не обмежена.

Часткові унікальні індекси SQLite:

- one_primary_contact(person_id, contact_type), коли is_active=1 та is_primary=1;
- unique_active_contact(person_id, contact_type, normalized_value), коли is_active=1.

CHECK обмежує тип, непорожнє значення, булеві прапорці й забороняє primary для архівного запису. Один номер дозволений різним людям. Архівний дублікат можна додати знову як новий активний запис; архів не редагується й не видаляється через UI. Повторне додавання не робить запис основним автоматично.

Router → services/contacts.py → repositories/contact_repository.py → SQLAlchemy. Мутації використовують service_transaction(immediate=True), що зберігає транзакційну політику SQLite. Зміна основного спочатку знімає попередній прапорець і flush у тій самій транзакції; помилка відкочує обидві зміни. Дії з наявним контактом перевіряють person_id та revision. Archive знімає primary, залишає value/метадані. Додаткового довільного primary немає.

Телефони: 7–15 цифр, необов'язковий початковий +, пробіли/дужки/дефіси. Нормалізація прибирає роздільники й початкове 00 міжнародного запису; original value зберігає введене написання. Країна не вгадується: локальний 067… не доповнюється до +380… і не вважається автоматично ідентичним йому. Це синтаксична перевірка, не підтвердження існування чи повноти номера. Код +380 не є обов'язковим.

Email: звичайний ASCII local-part з дозволеними символами/плюсом, без порожніх чи подвійних крапок; IDN-домен нормалізується через IDNA, перевіряються доменні компоненти. Нормалізований ключ порівнюється без регістру (явна політика дедуплікації). Internationalized Unicode local-part та quoted local-part зараз не підтримані. DNS/API/листи/SMS не використовуються. label — довільний текст до 100 символів, note — до 1000. Помилки не містять контактних значень; SQLAlchemy-помилки перетворюються на безпечне повідомлення без SQL/параметрів.

## HTTP та UI

- GET /persons/{person_id}/contacts — HTML списку, редакторів і архіву.
- POST /persons/{person_id}/contacts — створення.
- POST /persons/{person_id}/contacts/{id} — save, primary, unprimary або archive.
- GET /persons/{person_id}/overview — свіжий read-only HTML огляду.

Ці маршрути успадковують чинну політику кадрових сторінок; окремих нових дозволів, admin bypass чи системи авторизації не додано. HTML/JSON фрагменти мають Cache-Control: no-store. У мутації помилка повертає 400 JSON error/field, успіх — ok; клієнт залишає чернетку на місці, підсвічує поле/ставить фокус. Після успіху оновлюється список і огляд без перезавантаження анкети. Невідома мережева відмова залишає форму й радить перевірити фактичний стан перед повтором.

contacts.html містить два блоки, inline-додавання/редагування, власні підписи/примітки, основний/зняття основного, підтверджене архівування й історію. Копіювання відбувається лише за явним кліком через Clipboard API; mailto — звичайне безпечне посилання з URL-кодуванням. Кнопки × очищають поля чернетки, а не контакти в SQLite.

## Шапка та огляд

full_profile у person_read.py читає лише один активний PersonName/PersonRank; за кількох не обирає випадковий, а показує відсутність та попередження. Призначення читається на фактичну поточну дату через PersonAssignment → Position → StaffVersion з перевіркою обох періодів; неоднозначність не приховується вибором першого запису. Системний час створення не використовується для кадрового стану.

Формулювання служби береться лише з єдиного активного PersonServiceHistory з відомим явним service_type contract/контракт/за контрактом або mobilization/мобілізація/за мобілізацією. Для невідомого/неоднозначного джерела воно відсутнє. Статичний SERVICE_BASES сам по собі не є доказом виду служби людини.

Компактний header: 90 px портретна 3:4 заглушка SVG (80 px на мобільному), маленький підпис, великий ПІБ із великими літерами прізвища, звання й достовірне формулювання служби. Фото-моделі немає, випадкові аватари/завантаження не додані. Подальший рядок показує посаду/підрозділ або «Посада не зазначена». РНОКПП в шапці й оглядових картках немає; діагностичний TESTING/ORM-блок прибрано.

Порядок вкладок: general (за замовчуванням), names, ranks, positions, addresses, contacts, documents, family, events. Стабільні hash #contacts/#addresses/#names тощо, також ?tab=contacts; #addresses-registration відкриває потрібний адресний блок. Картки огляду мають реальні переходи. Огляд складається з чинних моделей і не має власних таблиць/полів; при переході на нього читається свіжий фрагмент. Contacts мутує огляд одразу, адреси — при поверненні на general. Старі endpoint-и географії та її JS/очищення/історія/заборона порожніх записів збережені; форми перенесені в addresses.

Positions показує поточне призначення й історію з реальним переходом /staff/history; нових правил редагування посад тут немає. Documents/family/events залишаються явно незавершеними розділами без фіктивних кнопок редагування. Names/ranks використовують старі компоненти й обробники. Навігація «Назад»/«До списку» збережена, вкладки прокручуються горизонтально, картки стають одноколонковими на телефоні.

## Безпечна міграція

Зупинити сервер та SQLite-клієнти. З кореня репозиторію:

```sh
python -m app.database.migrate_contacts --database data/database/project2.db
```

Міграція перевіряє попередню повну схему (включно з географічними source/link таблицями попереднього етапу), integrity/FK та чинні тригери. Maintenance lease і перевірка активних sidecar-файлів не дозволяють запускати її поверх активної БД. Створюється приватний SQLite backup *.before-contacts-UTC-RANDOM.sqlite3, потім під BEGIN IMMEDIATE виконується тільки DDL нової таблиці/індексів. Помилка відкочує весь DDL; попередні записи не змінюються. Повторний запуск — no-op, стороння неповна таблиця/відсутні індекси відхиляються для окремої перевірки. create_all для міграції не використовується. Автоматичного запуска при старті немає; робочу БД під час розробки не мігрували.

Для нової staging-бази повний reset використовує актуальний registry, тому таблиця автоматично створюється чинним init_db, без запуску міграцій. Звіт reset тепер також містить person_contacts (0: фіктивні номери/email не додаються). Коренева книга й довідники не змінені; reset основної БД не запускався. Попередні міграції обмежено їх первісними таблицями, щоб реєстрація PersonContact не ламала ранні етапи оновлення.

Chromium через column_visibility.cjs з COLUMN_STAGE=contacts/geography/name_cases: 6 + 10 + 10 сценаріїв, без pageerror. Перевірено незалежні основні контакти, серверні partial unique constraints, архів/re-add, owner/revision, збереження чернеток, rollback primary при відмові запису, безпечні повідомлення SQLAlchemy, ефективне призначення й явну службу, backup/idempotency/DDL rollback, Clipboard/mailto, live overview, hash і мобільну ширину 375 px. SQLite лише tmp_path/тестова, браузерний сервер — SQLite у пам’яті; робочу БД не використовували.
