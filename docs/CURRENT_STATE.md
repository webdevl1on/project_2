# Поточний стан project_2

Опис гілки `testing` за актуальним кодом. Результати виконаних перевірок компонента колонок наведені окремо нижче; решта опису не означає успішне наскрізне тестування всього застосунку. Карта компонентів і зв'язків — у [ARCHITECTURE.md](ARCHITECTURE.md).

## Що реалізовано

| Напрям | Наявна реалізація |
| --- | --- |
| Вебзастосунок | FastAPI `app.main:app`, Jinja2, HTML-форми та Bootstrap; чотири підключені роутери. |
| Люди | Список із сортуванням за одним ключем, створення та базове редагування, коротка й повна картки. Список показує активні ПІБ і звання; створення має дефект перенаправлення, наведений нижче. |
| Базові дані | Необов'язковий унікальний ІПН; дата народження з окремими nullable днем, місяцем і роком. Серверна перевірка повних і неповних дат, форматування у списку й короткій картці. |
| ПІБ | Обов'язкові прізвище та ім'я, необов'язкове по батькові та латинські варіанти; додавання запису історії, редагування, вибір активного й видалення неактивного з підтвердженням. |
| Звання | Довідник відмінкових форм, історія з реквізитами наказу, додавання, редагування, активація, видалення неактивного. Нове звання автоматично активне лише за відсутності поточного. |
| Штатні посади | Excel-завантаження довідника; таблиця посад, зайнятість, каскадні фільтри з кількома значеннями, пошук у меню, сортування, лічильники, збереження фільтрів у URL. |

| Пресети | Створення двома кнопками через одне Modal, підтвердження перезапису, негайне застосування, редактор через шестерню, окремі стрілки колонок, перейменування й підтверджене видалення. Пресети містять тільки видимі колонки та їхній порядок. |
| Історія таблиці | П’ять станів разом із поточним: колонки, їхній порядок, фільтри й каскадний порядок. Undo/redo відновлює серверну вибірку; сортування та ширини не є кроками історії. Підтримано reload і звичайні браузерні Back/Forward. |
| Призначення | Одна поточна посада на людину й один призначений на посаду; перенесення людини, заміна іншого призначеного та звільнення посади. |
| Вигляд таблиці людей | Клієнтське приховування окремих колонок; збереження налаштувань між завантаженнями сторінки не реалізовано. |
| Початкові дані | Створення таблиць та seed типів/підтипів подій, звань і посад. Робоча й тестова SQLite-БД мають окремі файли. |
| Тестові військовослужбовці | Окрема команда `python -m app.services.seed_test_people`: аркуш `persons`, перевірка даних, існуючий довідник звань, пропуск повторних РНОКПП, атомарне збереження кожної людини разом із ПІБ та званням. |
| Тести | Наявні pytest-тести валідаторів, дат, створення людини, зміни ПІБ і посад; окремий тест рендерингу сторінки посад. |

Базове редагування людини змінює поточний ПІБ **без** додавання історії; окрема дія «додати нове ім'я» створює історичний запис. Призначення на посади зберігають лише поточний стан, без дат та історії переміщень.

## Часткова реалізація та плани

- **Події:** моделі, довідники, валідатори та сервісні методи існують; вебмаршрутів немає, сервіс має дефекти. Це не готовий користувацький модуль.
- **Паспорти та історія служби:** ORM-моделі наявні; для паспортів є окремі валідатори й фабрика об'єкта. Повного CRUD через підключені роутери немає.
- **Повна картка:** вкладки «Посада», «Документи», «Сім'я», «Події» містять лише заглушки. Штатними призначеннями керує окрема сторінка `/person-positions`.
- **Пошук:** `search_person.html` не підключено; це не реалізована сторінка `/search`.
- **Зберігання налаштувань:** пресети та історія реалізовані локально в браузері й ізольовані за ID таблиці. API, персональне серверне збереження, авторизація та синхронізація між пристроями не реалізовані; є async-інтерфейс `PresetStorage` для майбутньої заміни. На робочих сторінках компонент поки підключено лише до таблиці посад.
- **Заплановано в [IDEAS.md](../IDEAS.md), але не реалізовано як завершені модулі:** табличний редактор і вставлення діапазонів Excel, користувацьке багаторівневе сортування, повний журнал змін із користувачем та відновленням, PostgreSQL, генерація Word-документів, авторизація/ролі й резервне копіювання.

`IDEAS.md` частково відстає від коду: неповні дати, модуль дат і призначення на посади вже мають реалізацію та тести. Наявність залежностей `python-docx` або PySide6 не підтверджує реалізацію генератора документів чи desktop-застосунку.

## Відомі проблеми за кодом

Наведені невідповідності встановлено читанням коду; у межах підготовки цієї документації вони не відтворювалися запуском застосунку.

| Ділянка | Проблема та наслідок |
| --- | --- |
| `app/routers/persons.py::create_person_from_form` | Після збереження повертає `303` на `/persons/{id}`. GET такого шляху відсутній; коротка картка має адресу `/person_detail/{id}`. Створення запису й успішний перехід на картку — різні результати. |
| `app/templates/person_detail.html` | Історія ПІБ звертається до `date_from` / `date_to`, яких немає в `PersonName` і `HistoryModel`. Стовпці дат не відображають фактичні поля; усі записи можуть позначатися «поточне» замість використання `is_active`. |
| `app/templates/person_detail.html` | Посилання «Видалити» веде на `/persons`; видалення людини не виконується, відповідного маршруту немає. |
| `app/templates/person_full_info.html` | Модальна форма ІПН надсилається на відсутній `/person_full_info_name_add/{id}`. Є налагоджувальний блок `TESTING` з виведенням ORM-колекцій. |
| Роутери ПІБ, звань, посад і повної картки | Обробка `ValueError` непослідовна: частину помилок не перетворено на HTTP-відповідь, частину приховано перенаправленням без повідомлення. Наприклад, додавання звання та відхилене видалення історії можуть повертати `303` без пояснення. |
| `service_person_create.py` + `persons.py` | Базова форма не редагує латинські поля, але POST передає їх як `None`, а `update_person` записує їх у поточний ПІБ. Отже, таке редагування може очистити латинські варіанти. |
| `service_common_person_func.py::CommonPersonFunc` | Старе оновлення викликає відсутні `DataGroupValidate.validate_rank_data`, `CommonPersonFunc.add_name`, звертається до відсутніх `PersonName.date_to` / `PersonRank.date_to`. Поточний роутер редагування використовує інший сервіс. |
| `service_for_person_event.py::create_person_event` | Викликає відсутній `CommonPersonFunc.get_person_or_raise`; підготовлений об'єкт події далі замінюється новим лише з `person_id`, втрачаючи обов'язкові дані. У `finally` написано `db.close` без виклику. Пошук події за датою також залежить від відсутнього методу перевірки людини. |
| `service_for_person_event.py::get_conflicting_events` | Параметр `exclude_event_id` додає умову рівності ID замість виключення; під час зміни події перевірка розглядає саме редагований запис замість інших. |
| `service_common_event_func.py::get_all_person_event` | Використовує `db.select`, хоча передана SQLAlchemy `Session` такого методу не має. |
| `PersonName` / `PersonRank` і сервіси історії | Правило одного активного запису підтримується логікою з вибором `.first()`, без відповідного унікального обмеження БД. Наявні дублікати активності можуть дублювати рядки у JOIN-вибірках. |
| `app/validators/person_validator.py::validate_names` | `isalpha()` відхиляє дефіси й апострофи; `capitalize()` змінює регістр. Це поточне обмеження введення українських ПІБ, а не підтримка всіх реальних варіантів. |

Старий шаблон `search_person.html` також звертається до вже відсутніх `person.pib`, `rank`, `position`, `phone`, `status`; підключеного маршруту він не має. `app/routers/person_service.py` не оголошує `router`, тому його закоментоване підключення не можна просто увімкнути.

## Робочі команди та межі перевірок

Нижче наведено загальні команди проєкту. Результати фактичних перевірок засівання людей і компонента колонок наведено в окремих підрозділах; це не перевірка всіх сторінок і сервісів.

З кореня репозиторію, у вибраному Python-середовищі:

```sh
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload
python -m pytest tests/
```

`requirements.txt` містить зафіксовані версії та має UTF-16-кодування. У коді використано синтаксис об'єднань типів і `datetime.UTC`; потрібен Python 3.11 або новіший з урахуванням сумісності залежностей. Точної версії інтерпретатора окремим файлом не закріплено.

Запуск сервера сам не викликає `init_db` чи seed. Для **нової порожньої** БД створення таблиць виконує `python -m app.database.init_db`; довідники завантажує `app.seeds.seed_structure.seed_all_structure(db)` з переданою сесією. Для наявної БД зі старої гілки `create_all` не оновить старі таблиці до поточних моделей. Автоматичних міграцій немає; збереження та перенесення існуючих даних потребує окремого завдання. Не використовувати reset як міграцію.

| Перевірка | Файли та охоплення |
| --- | --- |
| Базові дані й історія ПІБ | `tests/test_create_person.py`: створення з/без ІПН і дати, додавання історії, часткове редагування запису. |
| Неповні дати | `tests/test_birth_date.py`: календарні межі, форматування, створення й оновлення часткових компонентів. |
| Посади | `tests/test_person_positions.py`: фільтри, порожні значення, сортування, URL-параметри, рендеринг, перенесення та звільнення. |
| Валідатори | `tests/test_person_validator.py`, `tests/test_event_validator.py`: окремі правила полів; це не наскрізна перевірка модулів паспортів або подій. |
| Колонки | `tests/test_table_columns.py`: метадані, системна колонка, заголовки/комірки, опис URL-фільтрів. `tests/js/`: стан, сховище, пресети, фільтри та історія. `tests/browser/column_visibility.cjs`: базові, поетапні й наскрізні сценарії. |

У `tests/` немає окремих наборів для CRUD звань, сервісу подій або повного HTTP-сценарію створення людини з переходом за перенаправленням. У `test_validate_names_capitalize` результат обчислюється без `assert`, тому сам цей тест не підтверджує очікувану нормалізацію.

Для тестів слід явно вказувати каталог `tests/`: кореневий `test_seed_positions.py` при імпорті записує довідник у **робочу** БД. Фікстура `db` видаляє та створює таблиці `project2_test.db` перед кожним відповідним тестом. Під час перевірки Checkbox Tree Python-тести виконано з тимчасового робочого каталогу, щоб ізолювати файли SQLite; браузерний сервер використовував БД у пам'яті.

### Засівання тестових військовослужбовців

Запускати вручну з кореня репозиторію у Python-середовищі з установленими залежностями, проти **вже підготовленої** БД з поточною схемою та довідником `Rank`:

```sh
python -m app.services.seed_test_people
```

За замовчуванням використовуються кореневий `reference_data.xlsx` та `data/database/project2.db`. Для іншого файлу або ізольованої БД:

```sh
python -m app.services.seed_test_people --excel /path/reference_data.xlsx --database /path/test.sqlite3
```

Команда сама не створює файл БД, таблиці чи звання та не входить до загального засівання довідників. Основна БД під час розробки цього імпортера не засівалася.

Правила вхідних даних:

- Аркуш `persons`, заголовки першого рядка: `surname`, `name`, `patronymic`, `tax_number`, `birth_day`, `birth_month`, `birth_year`, `rank`. Дані починаються з другого рядка; повністю порожні рядки пропускаються, зайві колонки дозволені.
- ПІБ перевіряється чинними валідаторами: прізвище та ім'я обов'язкові; непорожні частини містять лише літери, 3–25 символів. Апострофи та дефіси чинний валідатор не приймає; імпортер цього правила не змінює.
- Неповні дати дозволені згідно з моделлю; невідомі компоненти залишаються `NULL`. Неможливі календарні дати відхиляються, відсутні компоненти не доповнюються вигаданими значеннями.
- РНОКПП зберігається рядком із 10 цифр. В Excel рекомендований текстовий тип для збереження початкових нулів. Числові клітинки підтримуються; початкові нулі відновлюються лише за явного формату `0000000000`. Короткий номер у форматі `General` відхиляється. Формули, помилки Excel, дробові й логічні значення не приймаються.
- Хоча модель дозволяє `tax_number = NULL`, **ця команда вимагає РНОКПП**: ПІБ і дата не гарантують унікальності. Без нього рядок пропускається з поясненням. Жодного штучного ідентифікатора не створюється.
- Звання — існуючий `Rank.code` або називний відмінок без урахування регістру та зайвих пробілів. Невідомі чи неоднозначні значення відхиляються; нові звання автоматично не додаються.
- Кожен рядок перевіряється, наявні люди з тим самим РНОКПП не змінюються. Нові записи зберігаються транзакцією на рядок. Після помилки одного рядка інші продовжують оброблятися; успішні рядки залишаються збереженими. Повторний запуск безпечний.

Вивід містить кількість знайдених, створених, пропущених рядків, окремо кількість наявних людей та помилок. Пропущені = наявні + помилкові. Повідомлення містять номер рядка й причину без персональних значень. Код завершення: `0` — без помилок, `1` — помилки окремих рядків, `2` — проблема файлу, структури Excel або доступу/схеми БД.

Перевірено на оновленому Excel з коміту `45cbc8a`, лише в тимчасовій SQLite з поточними моделями та канонічним довідником звань:

| Запуск | Рядків Excel | Створено | Пропущено | Помилок |
| --- | --- | --- | --- | --- |
| Перший | 15 | 15 | 0 | 0 |
| Повторний | 15 | 0 | 15 | 0 |

Після обох CLI-запусків у БД залишилося по 15 записів `Person`, `PersonName`, `PersonRank`; для кожного звірено ПІБ, РНОКПП, всі компоненти дати та звання. Тимчасову БД видалено після перевірки. Автоматичні тести імпортера разом із регресійними `test_create_person.py` і `test_birth_date.py` запускаються командою:

```sh
python -m pytest tests/test_seed_test_people.py tests/test_create_person.py tests/test_birth_date.py -q
```

Результат: **56 passed**. Тести виконано з тимчасового робочого каталогу та `PYTHONPATH` репозиторію, щоб також ізолювати БД наявних регресійних фікстур. Охоплення: ідемпотентність, збереження наявних даних, початкові нулі, неповні/помилкові дати, некоректні рядки й Excel, невідомі/неоднозначні звання, відкат усіх записів людини після збою пов'язаного запису та коди завершення CLI. Повний набір тестів застосунку в цьому завданні не запускався.

### Перевірка колонок, пресетів та історії

На ізольованих даних пройшли:

- **23 Python-тести**: `tests/test_person_positions.py` і `tests/test_table_columns.py` (метадані, HTML, URL-контракт і чинні фільтри/сортування/призначення).
- **19 Node-тестів**: стан/міграція v1, UUID включно з HTTP fallback, пресети без штучного обмеження кількості, перевірки назв/конфліктів/застарілих ключів, ширини, адаптер фільтрів і п’ять станів історії.
- **35 сценаріїв Chromium**: 10 базових, 8 пресетів, 5 Drag & Drop/ширин, 3 URL-фільтрів, 6 історії, 3 наскрізні. Перевірено справжні POST-призначення після перестановки DOM і застосування пресету, збереження однорівневого сортування, повернення вилученого фільтра через undo, reload, звичайні Back/Forward, незалежність двох таблиць та відсутність `pageerror`.

Команди з кореня репозиторію:

```sh
python -m pytest tests/test_person_positions.py tests/test_table_columns.py -q
node --test tests/js/*.test.cjs
PYTHON=.venv/bin/python CHROMIUM_PATH=/usr/bin/chromium node tests/browser/column_visibility.cjs
```

Python-перевірки цього завдання виконано з тимчасового робочого каталогу, щоб не змінювати наявні файли SQLite; наведений звичайний pytest-запуск використовує тестову БД. Браузерний сервер підставляє SQLite в пам'яті й генерує тестові дані. Нових Python-залежностей чи frontend-фреймворків не додано, ORM-моделі та схема БД не змінювалися.

Браузерному runner потрібні Playwright для Node, Chromium, `curl` та залежності Python-проєкту. `CHROMIUM_PATH` можна пропустити, якщо браузер встановлений Playwright. Для окремого етапу можна задати `COLUMN_STAGE=presets`, `layout`, `filters`, `history` або `integration`. Runner використовує справжні Bootstrap CSS/JS із чинного CDN; TLS-перевірку не вимикає. Тестовий маршрут із двома таблицями реєструється лише в окремому тестовому процесі.

Обмеження: перевірено Chromium; інші браузери та повний pytest-набір у цьому завданні не запускалися. Drag & Drop призначений для перетягування заголовків, resize підтримує pointer-події й стрілки клавіатури на межі. При недоступному `localStorage` показується помилка збереження; збереження пресетів і стану після перезавантаження тоді не гарантується. Історія змінює лише вигляд і фільтри, а не дані про призначення; ширини й поточне сортування при undo/redo зберігаються.

### Заплановане копіювання

Копіювання таблиць в Excel/Word ще не реалізовано. Заплановано перемикач режиму:

- **Excel** — табуляція між значеннями та перенесення рядків між записами.
- **Word** — HTML-таблиця через Clipboard API для коректного вставлення у Word.

Обидва режими мають використовувати поточний порядок **видимих** колонок і повні значення комірок, навіть коли CSS показує обрізаний текст. Повний текст уже зберігається в DOM у `data-column-value`; ширина є лише налаштуванням відображення.

`reset.py` і `reset_test_db.py` видаляють відповідні файли БД; `test1.py` і `test2.py` мають локальні Windows-шляхи та не є pytest-набором. Старі cloud-інструкції, створені для `main` з викликом `app.services.seed_all`, не відповідають `testing`: тут seed перенесено до `app/seeds/`, а вебточка входу — `app.main:app`.
