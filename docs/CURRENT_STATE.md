## PostgreSQL: поточний стан переходу (2026-11-01)

Реалізовано PostgreSQL 17 / psycopg 3 як цільову БД, явні PROJECT2_ENV/DATABASE_URL без SQLite fallback, три окремі назви БД та файлові каталоги. `0001_postgresql` створює 48 предметних таблиць, partial UNIQUE, три EXCLUDE, 32 тригери й функції Unicode/address/date. Startup лише перевіряє схему; наступні PostgreSQL-зміни — через Alembic. SQLite-міграції/reset збережені лише для legacy, reset відмовляє у production/PostgreSQL.

Repository отримує Session; write unit блокує конкретні рядки PostgreSQL і перевіряє revision, без глобального блокування звичайних операцій. Deadlock/serialization/lock timeout — контрольована відмова без retry. Правила дат, історії, документів і кадрового обліку не змінені.

`python -m app.services.seed_postgresql --dry-run`: read-only preview; apply — атомарне додавання довідників звань/подій і явно заданих names/geography/TCC/staff джерел. Відмінності наявних записів викликають конфлікт, без overwrite. Нові версії вакантні; людей і медичних файлів CLI не імпортує. Звичайний `seed_test_people` лишається legacy SQLite-інструментом.

Перевірено фактично:

- **41 passed** у PostgreSQL/config-наборі: 34 actual PostgreSQL + 7 configuration tests. Усі в project2_ci, випадкова схема на тест. CRUD предметних модулів, raw SQL guards, repeat Alembic/check, усі джерела засівання, read-only dry-run, ручні зміни й rollback.

## ПІБ, стать, нова форма та адміністрування

Реалізовано nullable Person.sex для старих записів і обов'язковий вибір статі для нових. /persons/new поетапно відкриває ПІБ, шість додаткових відмінків кожної частини, РНОКПП, неповну дату народження та Rank. Усі пов'язані записи зберігаються одним commit через існуючі сервіси; помилка залишає чернетку, успіх дає два переходи. Базова валідація ПІБ тепер зберігає регістр, підтримує короткі слова, апострофи/дефіси та 1–100 символів; РНОКПП й правила дат незмінні.

Глобальний NameDictionary і персональний PersonNameCases незалежні. Resolver використовує актуальні персональні значення, потім перевірений словник тієї самої статі, потім NULL із повідомленням. Словники за замовчуванням порожні; невідомі форми/стать не вгадуються. Ручні поля захищено від автозаміни, змінений binding позначається stale. Форми конкретного PersonName редагуються з історії ПІБ.

/admin містить захищені словники, редактор одного запису та Excel preview/confirm з додаванням або явним оновленням. За замовчуванням операції вимкнені без PROJECT2_ADMIN_TOKEN; налаштований доступ використовує HTTPS, підписану HttpOnly/SameSite cookie й CSRF. Для локальної розробки додано PROJECT2_DEV_ADMIN_OPEN=1: пряме loopback-з'єднання з Host localhost/127.0.0.1/::1 відкриває всі адміністративні функції без токена, входу та CSRF. LAN/зовнішні клієнти, forwarded-заголовки й cross-site запити не отримують цього винятку. Без перемикача чинний захист незмінний. Повної системи користувачів/ролей поки немає. Імпорт має перевірку всього файлу, лічильники, revision, квитанцію повтору та один commit/rollback; персональні форми не змінює.

Excel-формат оновлено до шести аркушів за категорією/статтю; колонку sex прибрано, системні заголовки — рядок 1, українські підписи — рядок 2, дані — з рядка 3. Генератор, файл шаблону й підказка /admin узгоджені. Перевірки адаптації: 420 Python passed та 10 браузерних сценаріїв ПІБ/адміністрування, включно з Excel preview/confirm, оновленням і дублікатами; дані ізольовані, два наявні deprecation-попередження. Бізнес-правила, моделі, preview/транзакції та авторизація незмінні.

Точний формат, запуск і обмеження — [NAME_CASES.md](NAME_CASES.md). Порожній файл: [templates/name_dictionaries_empty.xlsx](templates/name_dictionaries_empty.xlsx). Робоча БД не змінювалася. Новому seed persons потрібна колонка sex; reference_data.xlsx оновлено для повного reset: синтетичні люди зі статтю й географією, два рядки заголовків. ## Архітектурний аудит та рефакторинг

Перевірено всі п’ять активних роутерів, сервіси осіб, штатної історії, таблиць, подій, тестове засівання та діагностичні модулі. Карта проблем до змін: предметні ORM-запити в роутерах; невикористаний PersonRepository; власні SessionLocal в подіях; commit без однакового rollback-захисту осіб/ПІБ/звань; спільний вибір історії через залежність picker від сервісу таблиці; взаємна залежність staff_service/staff_import через локальний імпорт валідатора; імпорт templates із сусіднього роутера; зламане невикористане CommonPersonFunc.update_person і діагностики із запитами під час імпорту.

Виконані етапи:

1. Підключено PersonRepository до створення/редагування й читання осіб, ПІБ/звань і засівання. `person_read.py` готує дані сторінок; сервісні записи мають service_transaction і можливість commit=False.
2. StaffRepository містить доступ до структури/версій/посад/призначень, staff_read.py — сценарії читання. Створення структури перенесено з роутера до StaffService. Чинний write_unit із BEGIN IMMEDIATE/revision/rollback збережено. Спільну валідацію реквізитів винесено до position_validator; шаблони налаштовує app/templating.py.
3. PositionTableRepository містить joins/фільтри/сортування таблиці; SQL більше не будується в роутерах і кадрових/табличних сервісах. history_selection спільний для таблиці та picker. Форматування значень і підготовка варіантів фільтрів залишилися у сервісі читання.
4. EventRepository містить SQL подій; PersonEventService отримує зовнішнє db=, не commit/rollback/close його. Окремі виклики через session_factory сумісні. Невикористаний зламаний update_person видалено після перевірки всіх згадок, фабрику паспорта залишено; діагностики запускаються лише явно через main.

Моделі, схема/SQLite-тригери, точні дати подій і штатних періодів, неповні предметні дати, системний UTC, кадрові правила й URL-контракти не змінені. Jinja2/JavaScript/CSS не редагувалися. Сесійний життєвий цикл і правила складання транзакцій — [ARCHITECTURE.md](ARCHITECTURE.md#єдині-правила-транзакцій).

Обмеження: ORM-колекції картки залишаються lazy; єдиний активний ПІБ/звання не закріплено новими обмеженнями БД; помилки старих person-роутерів не уніфіковано. Сервісний контракт списку конфліктів збережено; у новому редакторі подій межі періодів уже включні, а одна попередня відкрита подія може завершуватися атомарно. Прямі ORM-запити в окремих CLI-довідниках app/seeds залишено в межах їхнього чинного транзакційного сценарію. Для вже flush-нутих сторонніх змін не покладатися на pending-guard: спільний запис вимагає явного зовнішнього власника й commit=False/db=.

## Версії штатів та історія: поточний етап

Реалізовано StaffStructure → StaffVersion → Position → PersonAssignment; поточний стан — вибірка на дату, без дублюючої таблиці. На /person-positions є вибір версії/дати, новий трирядковий пошук людей і модальне підтвердження переведення; зайнята іншою людиною посада не звільняється автоматично. /staff/history дозволяє внесення заднім числом, виправлення запису й реквізитів конкретної посади, явне атомарне закриття версії та її призначень.

Імпорт кнопкою «Завантажити штатну структуру»: тільки positions з чинними заголовками; попередня перевірка, окреме підтвердження, одна транзакція, захист повтору. Мінімально виправлено наявні помилки створення/редагування/читання подій, потрібні для backdated сценаріїв.

Повні правила, схема, джерела даних, межі SQLite, формат імпорту й ручні команди пересоздання/засівання — [STAFF_HISTORY.md](STAFF_HISTORY.md). **Наявна БД не пересоздавалася.** Новому коду потрібна нова схема; create_all не мігрує стару. Засівання довідників тепер не створює штат без явно вказаних назви/дат.

Охоплено також редагування версій/посад, закриття версії та створення структури.

### Централізований каталог полів

Реалізовано 55 інформаційних колонок: штатна посада (11), звання (10), особисті дані (10), служба (6), документи (6), системні дані (12). Із «№» та формою призначення — 57; попередні 12 видимі типово. Перелік кожного поля, моделі, атрибута, типу, nullable, фільтрації та сортування — у [TABLE_FIELDS.md](TABLE_FIELDS.md).

`app/table_fields.py` містить повторно використовувані визначення, `app/table_columns.py` — вибір груп/ключів і перевизначення для конкретної таблиці. Додавання поля з каталогу не потребує ручної предметної гілки в HTML. Одержання значень/форматування на сервері; дозволені SQLAlchemy-джерела явно визначені, довільні клієнтські ключі не перетворюються на SQL.

Для ПІБ, звання, паспорта й служби погоджено: єдиний запис → він незалежно від активності; кілька → єдиний активний; немає → `-`; неоднозначність → `-` і попередження. 41 скалярне поле та шість дат мають каскадні фільтри. Всі 55 полів мають типізоване однорівневе сортування. Вісім точних системних DateTime сортуються без втрати часу, фільтрацію для них відкладено. Порожні значення показуються як `-`, відомі частини дат — спільним форматтером з `_`. Нові фільтри використовують той самий URL-контракт і filter_order; приховування реально очищає відповідний фільтр, undo відновлює його. Старі пресети збережено без зміни формату чи перезапису.

Перевірки на поточному коді: **309 Python-тестів**, **23 Node-тести**, **51 сценарій Chromium** — усі пройшли. Python-запуск виконано з окремого тимчасового каталогу з посиланням на app та PYTHONPATH репозиторію; стара фікстура db працювала лише з тимчасовим файлом. ### Універсальні предметні дати та системний час

Народження, дати паспорта, наказу про звання та історії служби підтримують незалежно невідомі частини. Для останніх п'яти дат додано 15 nullable Integer; старі Date залишаються проєкціями повних значень. Компоненти є джерелом даних, пропущені частини — NULL, форматування — один `_` для кожної невідомої складової. `PartialDateMixin` перевіряє й синхронізує значення при ORM insert/update. Уточнення дати наказу змінює існуючий запис звання; новий запис лише через уточнення не створюється.

Схему SQLAlchemy змінено за погодженням для поточного етапу розробки без Alembic та перенесення старих тестових даних. **Існуючі файли SQLite не змінювалися й не пересоздавалися.** Для роботи оновленого застосунку потрібна нова БД поточної схеми або ручне пересоздання вибраної тестової. `create_all` не оновлює старі колонки; seed-команди перевіряють схему перед записом. Точні команди, перевірка захисту файлів і наслідки `--recreate` — у [DATE_SYSTEM.md](DATE_SYSTEM.md#створення-та-повторне-засівання).

Спільний компонент введення використовується у формі людини та модальних формах додавання/редагування звання. Є клієнтська календарна перевірка та серверні 400 для некоректних дат; підтримано старий точний POST `rank_order_date`. ПІБ, дати та системні часові позначки не додаються до пресетів: вони зберігають лише видимість/порядок колонок. Повних вебформ паспортів та історії служби не додано.

Таблиця посад має 56 колонок, типово видимі 12. Шість предметних дат (повний перелік у [TABLE_FIELDS.md](TABLE_FIELDS.md)) використовують ті самі меню, possible-match фільтри, шість пріоритетів і сортування невідомих частин після відомих. Дата наказу типово прихована, її можна ввімкнути Checkbox Tree. Кожна дата має власні URL-фільтр і пріоритет. Приховування очищає лише її фільтр; undo/redo й браузерні Back/Forward відновлюють узгоджені колонки та серверну вибірку. Відсутній вибраний запис людини/звання/паспорта/служби не вважається наявним записом із невідомою датою. Старий ключ `/persons?sort_by=birth_year` продовжує використовувати спільне сортування повної дати.

Для possible match перевіряється існування сумісної календарної дати. `29.02._` не відповідає лише невисокосному року. `_._._` може відповідати умовам, якщо поле дозволяє неповноту. Пріоритет місяць/день/рік — календарне сортування, не пошук найближчого дня народження.

Звичайні форми не приймають системні часові позначки. Audit Log не реалізовано.

### Копіювання та приховування з меню заголовка

Реалізовано спільний `TableSelection` у `app/static/js/table_selection.js`. Виділення: одна комірка, прямокутник мишею, Shift для розширення від опорної комірки, Ctrl/Meta для додавання окремих комірок і діапазонів. Escape очищає виділення. Ctrl/Meta+A та Ctrl/Meta+C не перехоплюються — це стандартні комбінації браузера. Клавіші редагування у формах, select, textarea та contenteditable не перехоплюються. Колонка форми призначення й заголовки не копіюються; номер рядка копіюється.

Лише кнопка «Копіювати» експортує поточне виділення. У меню заголовка додано «Виділити колонку» для вибору всіх її завантажених видимих комірок. Вертикальний drag по тексту прізвищ перевірено окремо; під час перетягування вимикається нативне текстове виділення, попередній текстовий діапазон очищається. Поруч розташований перемикач Excel/Word, типово Excel; формат зберігається окремо для кожного table-id. Excel — text/plain TSV; Word — справжня HTML-таблиця та одночасний text/plain. Табуляції/перенесення/лапки коректно екрануються для TSV, HTML екранується. Копіюються повні відображувані значення (включно з неповними датами й `-`), без кнопок, форм та іконок, лише у видимому DOM-порядку. Для Ctrl-діапазонів правило — спільний прямокутник із порожніми невибраними комірками всередині; приховані колонки пропускаються.

Clipboard API доповнено legacy copy-event/execCommand fallback. За доступності лише тексту в режимі Word показується «HTML для Word недоступний. Скопійовано лише текст TSV»; за повної відмови показується помилка. Обмеження залежать від браузера, HTTPS/localhost та дозволів; фактичне вставлення в настільні Word/Excel тут не перевірялося.

У меню заголовків (також дат і системних DateTime) додано «Приховати колонку». Дія проходить через чинний commitLayout/TableTimeline: Checkbox Tree оновлюється, лише власний активний фільтр реально знімається з URL, Undo повертає колонку й фільтр, Redo повторює приховування. Системна нумерація недоступна для приховування; остання інформаційна колонка захищена. Виділення очищається після зміни layout, зберігається під час resize. ## Уточнений процес і редактор ВЛК

Додано INTERRUPTED тільки після PLANNED. Дати початку (чинний planned_on), завершення (ended_on), довідки (issued_on) і переривання незалежні, календарно точні або NULL. Перерваний запис не відновлюється: наступне проходження — новий запис/направлення без автоматичного копіювання документів. NEEDS_EXAM/PLANNED потребують поранення, документа-підстави або опису; PLANNED — також початку. COMPLETED потребує дати довідки, номера й придатності; INTERRUPTED — початку/дати/причини переривання. Старі неповні COMPLETED читаються й лишаються актуальними за чинним вибором, але редагуються лише із заповненими обов’язковими полями.

Контроль прив’язано до конкретного PersonnelTask.exam_id. Перше проходження за пораненням використовує injury_vlk, наступні/незалежні мають exam_vlk без дублів. Нове незавершене ВЛК не закривається старою завершеною довідкою; INTERRUPTED лишає питання відкритим. Явне «ВЛК не потрібна» не переписується; фактично відкритий медичний запис контролюється окремо. injury_award, документи/файли, дата PersonEvent та вільний доступ не змінені.

## Security 1.2 — керування користувачами (2026-11-05)

У feature/security від abaed84 реалізовано розділ «Адміністрування → Користувачі»: список ID/логінів/ролей/точних UTC, окремі стани вимкнення й тимчасового lockout, створення Admin/Editor/Viewer, відображуване ім’я/роль із revision, блокування, скидання чужих паролів, відкликання всіх сесій та читабельний аудит. У навігації кожної ролі — зміна власного пароля з поточним/новим/підтвердженням. Паролі scrypt 12–128, повторення старого відхиляється, всі сесії після успішної зміни відкликаються. Помилки GUI зберігають несекретні чернетки, очищуючи тільки паролі.

Master має всі чинні права Admin, захищений від змін звичайним Admin і від власного пониження/вимкнення; другого Master не допускає partial UNIQUE. Мінімум один активний персональний Admin не включає Master або legacy-технічні записи. Єдиний початковий Admin може стати Master лише явною CLI-процедурою ID+пароль+підтвердження; за нульового числа окремих Admin список користувачів попереджає Master. Створення першого Admin усуває перехідний стан. Немає автоматичного підвищення за логіном admin чи ім’ям master.

AccountAudit атомарний зі зміною User/сесій, містить реального автора HTTP-сесії, дозволені before/after та точний UTC, без паролів/хешів/токенів. Append-only й account guards працюють у PostgreSQL та ізольованій тестовій SQLite. Advisory xact lock + FOR UPDATE/revision не дозволяють конкурентно прибрати всіх Admin; відкликання сесій синхронізоване зі входом. Кадрові моделі/правила не змінені.

## Security 1.3 — MFA та захист сесій (2026-11-07)

Реалізовано двоетапний вхід: пароль створює тільки обмежений п’ятихвилинний AuthFlow у БД; повна UserSession — лише після підтвердження TOTP/Passkey або одноразового резервного коду. Усі персональні ролі, включно з чинним Master, проходять MFA без винятків. Старі password-only сесії з NULL mfa_verified_at відхиляються. Початкове налаштування не відкриває предметних даних і не змінює ID/роль/пароль.

Додано TotpFactor/Passkey/RecoveryCode/AuthFlow/MfaKeyState, FK/index/CHECK, зашифрований TOTP зі стабільним зовнішнім Fernet key ring, QR/ручний секрет, перевірку кодом перед активацією, replay guard та lockout. WebAuthn бібліотека перевіряє challenge/origin/RP/signature/presence/обов’язковий UV/лічильник; кілька ключів, перейменування/відкликання. 10 випадкових резервних кодів показуються один раз, зберігаються лише digest, одноразові та замінюються тільки явно. Підтверджена заміна втраченого TOTP можлива після резервного входу без Passkey.

UserSession має точні UTC created_at/last_activity/expires_at/mfa_verified_at та несекретний випадковий ID. Idle — 15 хвилин конкретної сесії, абсолютна межа — 8 годин, fresh MFA — 5 хвилин для критичних дій. Фонові GET/refresh/polling не оновлюють last_activity; погоджений GUI надсилає activity тільки на trusted взаємодію, а локальний таймер лише попереджає. Власні сесії доступні у навігації; можна завершити одну іншу чи всі інші, не отримуючи токенів/хешів.

AccountAudit розширено без дублювання механізму. MFA/коди/сесії та аудит атомарні; примусове відкликання також анулює незавершені входи. Fresh-MFA адміністративне recovery документує перевірку особи, відкликає фактори/коди/flow/сесії та вимагає нового налаштування. Admin не скидає Master; серверне відновлення Master — явна локальна Administrator/root CLI із поточним паролем, причиною й підтвердженням, без emergency endpoint/token.

Новий head **0007_mfa_sessions** після 0006, попередні ревізії не змінені. Робочі БД/користувачі й testing не змінювалися, commit/push/merge/reset не виконувалися. Перед ручним upgrade потрібні backup БД, постійні MFA-ключі та їх окремий backup, точні RP/origins, нові залежності; після upgrade — явне mfa_keys --initialize. Startup перевіряє marker/config, не мігрує й не генерує ключ. Деталі, ротація, локальна перевірка й межі — [SECURITY.md](SECURITY.md), [POSTGRESQL_SETUP.md](POSTGRESQL_SETUP.md).
