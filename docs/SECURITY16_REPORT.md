# Security 1.6 — звіт реалізації та перевірок

Гілка `feature/security`, початковий чистий HEAD `a5a4a2e`. Перевірено актуальну `origin/testing=00cf012`: початковий HEAD містить її та дев’ять наступних комітів; `testing` не змінено. Commit/push виконуються лише за окремою прямою вказівкою користувача. Робочі PostgreSQL, MFA-ключі, користувачі, документи та наявні резервні копії не змінювалися.

## Реалізовано

- Самодостатній погодинний full, окремий щоденний full, криптографічний verify та обов’язковий фактичний ізольований drill саме створеної копії. Статуси цілісності й успішного відновлення розділено. OS/PostgreSQL lease охоплює весь цикл; підписана черга переживає перезапуск, дозволяє одну повторну спробу й повідомляє про остаточну помилку. Автоматичного видалення постійних копій немає.
- Щоденний аварійний комплект о 18:00 Europe/Kyiv з DST і відновленням пропущеного запуску після повернення живлення. Три книги: `Персональні_дані.xlsx`, `Події_та_служба.xlsx`, `Аудит.xlsx`. Експортуються чинні та історичні предметні таблиці за явним переліком ORM, персональні ID/ПІБ, повні й неповні дати, українські заголовки та фільтри. Великі аркуші/тексти діляться без мовчазного обрізання; формули записуються як текст. Готовність публікується після перевірки всього комплекту, старі версії зберігаються.
- Накопичувальні документи й фото: безпечні Windows-назви, ПІБ/наявна точність народження, розрізнення однакових людей за `person_id`, тип/підтип документа та окрема нумерація, дедуплікація source ID + SHA-256, збереження вилучених/замінених оригіналів і попередніх папок після зміни ПІБ. Ідентичність фотографії не вгадується з її назви.
- Серверний USB-worker: тільки дозволений фізичний USB/Volume GUID, NTFS, увімкнений повністю завершений BitLocker, unlocked/writable, перевірка SID і місця, повторна перевірка носія, захист reparse/junction та атомарний запис без заміни наявного файла. Різний SHA-256 у наявного файла є конфліктом. Новий Excel завжди має окрему версію; пароль BitLocker застосунок не отримує.
- `/admin/backups`: стан, окремі integrity/drill, черга, аварійний комплект, вибір серверного USB, щотижнева/ручна статистика PostgreSQL і каталогів, кількості, місце, приріст за сім днів і попередження. HTTP не виконує копіювання чи privileged PowerShell, не видає повні архіви та не запускає restore.
- `/admin/audit`: системний, предметний та backup-аудит; дата/період/місяць, ID/логін автора, операція, текстовий пошук, кілька рівнів сортування, пагінація й TXT усього відфільтрованого результату. Спільна таблиця з налаштуваннями колонок і читабельний modal змінених полів. ACL застосовується до рядків/значень **до** пошуку, кількостей, сортування та експорту.
- Аудит наявних джерел доповнено лише прогалинами: перевірені події входу/невдалого входу/MFA/виходу та `SubjectAudit` для предметних ORM-операцій без власного журналу. Автор береться з серверного контексту; неідентифікований автор залишається NULL. Зміна й аудит атомарні, журнали append-only, вигаданої старої історії немає. Старий екран журналу акаунтів також коректно показує невідомого автора/акаунт.

## Повноваження та повторне використання

Master/Admin можуть читати стан/журнали, створювати й перевіряти копії та запускати аварійний/USB-експорт; ручні критичні дії потребують чинної MFA за п’ять хвилин і CSRF/Origin. Використано наявний reauth modal: чернетка/вибір зберігається, критичний POST автоматично не повторюється. User цих системних дій не отримує.

Повний аварійний експорт — окреме погоджене системне повноваження Master/Admin з результатом лише в перевіреному серверному/USB-каталозі. Воно не додає Master звичайних предметних read-grants. API повертає стан, ID, кількості/розміри; немає довільного destination або предметного JSON/download. Звичайні анкети, файли та предметний аудит/TXT залишаються під чинним ACL. Ключі, дозвіл автоматизації та серверний restore залишені тільки Master; регулярний worker користується вузьким підписаним дозволом, який можна відкликати.

Повторно використано `User`, `UserSession`, MFA/TOTP/WebAuthn, CSRF, сесії 15 хв/8 год, Security 1.4 ACL, `DocumentStorage`, наявні предметні аудити, snapshot gate, advisory/OS lease, `BackupEngine`/repository, AES-256-GCM/HMAC, окрему капсулу секретів, restore-plan/apply/drill Security 1.5, `ProfileDates`, Bootstrap та спільні таблиці. Нових сторонніх залежностей немає; Excel використовує вже наявний `openpyxl`.

## Налаштування Windows перед використанням

Покрокові команди й ручні сценарії: [BACKUP_AND_RESTORE.md](BACKUP_AND_RESTORE.md).

1. Підготувати різні приватні каталоги джерел, backup, капсул, ключів, staging, drill і аварійного комплекту поза static/Git; BitLocker внутрішніх дисків, NTFS ACL та довірені service SID окремо від звичайних читачів архіву.
2. Задати фактичний release, PG17 tools, стабільні різні backup keyring, зберегти чинні MFA/signing secrets окремо; перевірити офлайн-копії ключів. Задати `emergency_enabled`, ліміти, Volume GUID allowlist, `archive_sids`, `service_sids` та alert command.
3. Підготувати окремий PG17 CI-кластер і control `project2_ci`, без доступу до робочої БД. Master затверджує drill/emergency automation на обмежений строк або явно до відкликання; дозволи прив’язані до середовища.
4. Зареєструвати перевірений worker у Task Scheduler під довіреним OS-акаунтом (`StartWhenAvailable`, `IgnoreNew`, без time limit); перевірити права PowerShell/BitLocker. Web-процес підвищувати не потрібно.
5. Якщо потрібні персональні папки портретів, надати захищений `photo_index`: чинна модель не містить надійного Person–photo зв’язку. Без нього фото не губляться, але потрапляють до «Нерозподілені фото».
6. Master/Admin зі свіжою MFA вибирає **серверний** USB у `/admin/backups`; результати — `Project_2/Excel/<унікальна версія>` і накопичувальні `Документи`. Дозволені архівні користувачі можуть редагувати Excel, попередні версії не замінюються. На носії наразі потрібна призначена Windows-літера для discovery; запис іде за перевіреним GUID.
7. До регулярного використання виконати реальний ізольований drill, два погодинні цикли, restart/power-return, помилки носія/місця та сповіщення; перевірити ручне читання Excel після розблокування, повноту своїх фотографій і архівні NTFS ACL.

## Неперевірене та обмеження

- Реальний Windows-ПК, USB, BitLocker, Task Scheduler, `icacls`/Win32 handle rename, фізичне відключення й повернення живлення **не перевірялися**. Їхні результати не підмінено mocks.
- Якщо backup/drill перевищить годину, паралельного запуску не буде, але ціль RPO може порушитися. За вимкненого ПК нові точки не існують. Порожній `alert_command` дає лише журнал/панель без зовнішнього повідомлення.
- Повні копії, Excel і документи автоматично не видаляються. Потрібні контроль місткості, місце для staging/CI та окреме усвідомлене ручне рішення щодо обслуговування.
- Зведений аудит наразі відбирає дозволені записи в пам’яті; дуже великі журнали потребують вимірювання й оптимізації. Окремий підписаний метаданими маніфест обмежений 128 MiB; перевищення зупиняє нову публікацію, старі версії залишаються.
- Посилання особи на фотографію без захищеного індексу не відновлюється здогадками. Прямі SQL/ручні файлові зміни поза прикладними сервісами потрібно узгоджувати з snapshot gate; новий ORM-аудит не обіцяє журналювання довільних команд власника БД.
- Звичайний HTTP restore та автоматичний cutover у робоче середовище відсутні за вимогою. Offline Master recovery зберігає перевірку реальної особи/MFA й відновлення спочатку лише в порожню ізольовану ціль.
- Після розблокування Excel та документи — відкриті персональні дані. Їхню фізичну безпеку забезпечують BitLocker, NTFS і контроль серверного/USB-доступу, а не браузерний ACL під час автономного читання.
