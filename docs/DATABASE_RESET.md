# Повне тестове засівання SQLite

`reset.py` створює **тестовий набір**, а не мігрує чи зберігає персональні дані. Імпорт модуля не виконує reset. Перед запуском зупиніть сервер і всі SQLite-клієнти. Запускати з кореня репозиторію в підготовленому Python-середовищі.

```powershell
python reset.py --dry-run
python reset.py
```

Перша команда перевіряє файли/контрольні суми/формати/дублікати/FK/дату штату/місце на диску без створення SQLite. Друга показує абсолютний шлях (`data/database/project2.db` за замовчуванням), попереджає про заміну даних і вимагає точного `RESET`. Інший ввід скасовує операцію. Основна БД не видаляється до побудови й повної перевірки нової.

Для автоматизованої ізольованої перевірки:

```powershell
python reset.py --database data/database/project2_test.db --yes
```

`--yes` дозволено тільки з явним `--database`: назва файла має містити `test`, а шлях не може вказувати на основну БД. Не використовуйте цю опцію для робочих даних. Для власних копій джерел є `--excel`, `--names`, `--geography`; типові значення вказують на кореневу книгу й дві папки в `reference_data/`.

## Етапи та захист

1. Preflight: контрольні суми пакетів, manifest/validation/file_validation, усі шість словникових аркушів/два рядки заголовків, CSV UTF-8 BOM з `;`, зовнішні UUID, офіційні коди, дублікати, FK та узгодженість ієрархії. Перевірка positions повторно використовує staff_import; дата штату задана явно в seed_config.
2. Підтвердження та exclusive maintenance lease. Вебзастосунок тримає shared lease під час роботи, тому сервер і reset не можуть використовувати ту саму БД одночасно. Існування WAL/SHM/journal блокує reset; ці файли автоматично не видаляються. Для сторонніх клієнтів додатково перевіряється доступність SQLite-блокування; Linux також перевіряє відкриті файлові дескриптори інших процесів. Усі сторонні процеси однаково потрібно зупинити, особливо старі версії сервера без lease.
3. Файл `.NAME.staging-*.sqlite3` створюється в тому самому каталозі з приватними правами. init_db створює поточну схему й чинні тригери; старі міграції на порожній БД не запускаються.
4. Звання/події → словники → географія → штат → люди разом з початковими географічними даними → необов'язкові assignments. Кожна людина, її ПІБ, звання й адреси атомарні. Великі географічні дані читаються потоково, вставляються Core-пакетами по 500, в одній транзакції компонента; не накопичуються сотні тисяч ORM-об'єктів. Штат створюється через штатний імпортер, а не обхід його перевірок.
5. Перевіряються integrity_check, foreign_key_check, поточні таблиці/тригери, кількості проти пакетних manifest/validation, активні ПІБ/звання, стать та читання адрес чинним сервісом. Файли повторно перевіряються, зміна джерел скасовує публікацію.
6. Сесії/engine staging закриваються. Попередня БД копіюється через SQLite backup API у `NAME.before-reset-UTC-RANDOM.sqlite3` (0600). Нова замінює її через os.replace у межах одного файлового тому. При помилці попередня БД залишається; прибирається тільки staging цього запуску. Якщо заміна ОС не вдалася, backup також залишається. Службовий `.maintenance.lock` є постійним coordination-файлом, не ознакою живого процесу; його не потрібно видаляти. Файли БД/backup/staging/lock не комітяться.

Жоден механізм не замінює вимоги закрити сторонні редактори SQLite: вони не беруть участі в lease. Запуск нових сторонніх writer-процесів під час reset заборонений.

## Особливості джерел

- Географія: CSV, без Excel-дублікатів; 249 країн, 27 регіонів, 136 районів, 1772 громади, 29703 населені пункти, 108 внутрішньоміських районів, 327985 однозначних вулиць, 0 aliases. Київ/Севастополь зберігають окремі адміністративні ролі, як у джерелі, без штучних громад. Внутрішньоміські райони — окрема таблиця, не адміністративні district.
- Не імпортуються `streets_unresolved.csv` (86688), `hierarchy_issues.csv` (звіт про 8 прогалин), `countries_excluded.csv` (2), сирі архіви та альтернативні Excel-експорти. Первинні файли перевіряються за sources.json, але не обробляються як окремий набір.
- Відмінки: чотири `project_2_dictionary_*.xlsx`, 36880 рядків, без `manual_review.xlsx`. Прийняття цього пакета надає is_verified=True для чинного resolver. Це **операційно прийняті автоматично перевірені форми**, а не твердження про ручну академічну перевірку кожного слова. Персональні PersonNameCases не переписуються.
- `.gitattributes` нормалізує CSV до LF, тоді як пакетні SHA256SUMS містять суми вихідного CRLF. Спочатку перевіряється байтова сума; якщо вона не збігається, тільки для CSV перевіряється відновлення канонічного CSV UTF-8 BOM/`;`/CRLF через csv.reader/writer у пам'яті, зі збереженням LF всередині quoted-полів. Файли не виправляються; про політику явно повідомляється. Зміна значень або інші розбіжності блокують reset.

positions збережено з початковим XML, формулами й кешованими значеннями (10 посад). Збереження книги бібліотекою, що видаляє кеш формул, може вимагати перерахунку в Excel перед імпортом; preflight не вигадує значення замість формул.

persons: системні ключі рядок 1, українські підписи рядок 2, дані з рядка 3. Дев'ять основних колонок і географічні birth_*, registration_*, actual_*; точний склад — seed_test_people.GEO_COLUMNS. Поточна книга має 4 навмисно вигадані особи, обидві статі, часткові дати/місця народження та ручну географію. РНОКПП з префіксом нулів, будинки й квартири синтетичні; вулиця взята з пакета з підтвердженим settlement_id. Це не твердження про проживання реальної людини. Географічні назви однозначно прив'язуються тільки в межах вибраних батьків; неоднозначні/невідомі залишаються текстом. Відсутній блок адреси не створюється. Повторний РНОКПП пропускається без зміни наявних даних.

seed_config: `version_name, structure_code, valid_from, valid_to`, підписи рядок 2, один запис рядок 3. Дати — явні повні ISO-рядки; valid_to може бути порожнім. Немає значення «сьогодні за замовчуванням». Приклад книги: «Навчальний штат 2026», training, 2026-01-01, без завершення. Нова версія вакантна.

Необов'язковий assignments: `tax_number, position_number, date_start, date_end`, підписи рядок 2, записи з рядка 3. date_start обов'язкова повна ISO-дата, date_end порожня або повна; посада належить seed-версії, РНОКПП — тестовим людям книги. Відсутність аркуша означає 0 призначень. Помилкові посилання/періоди/конфлікти зупиняють reset; запис проходить StaffService.

## Відновлення backup

Зупиніть сервер і SQLite-клієнти, переконайтеся у відсутності активних WAL/SHM/journal. Збережіть поточну БД окремо, потім скопіюйте потрібний backup на точний шлях основної БД:

```powershell
Move-Item data/database/project2.db data/database/project2.before-restore.sqlite3
Copy-Item 'data/database/project2.before-reset-<UTC>-<RANDOM>.sqlite3' data/database/project2.db
```

Підставте реальне ім'я backup; не перезаписуйте іншу збережену копію. Backup відновлює також стару схему: використовуйте сумісну версію застосунку або відповідні явні міграції. Автоматичного відновлення/видалення backup немає. Для гарантії збереження адрес не запускайте reset замість міграції робочої БД.

## Результат перевірки пакета

У cloud виконано dry-run повного пакета, створення й заміну лише /tmp/project2-full-reset-test.sqlite3 з backup та окреме повторне засівання всіх компонентів. Отримано 21 звання, 7 типів/15 підтипів подій, 36880 словникових рядків, географічні кількості вище, 10 посад, 4 людини, 4 місця народження, 8 адрес, 0 призначень. На повторі нових записів 0; усі 8 адрес matched, resolver отримує відмінки відомих імен зі словника. Основна SQLite не скидалася. Повний Python-набір: 450 passed; Node 31; браузер 15 сценаріїв (GUI-словники та географія).
