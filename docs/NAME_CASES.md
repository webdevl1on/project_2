# ПІБ, відмінки та адміністрування

Поточна реалізація `testing`. Автоматичного відмінювання за суфіксами, визначення статі за ПІБ або великих вбудованих словників немає. Невідоме значення лишається порожнім.

## Дані й відповідальність

- `Person.sex`: `male`, `female` або NULL для збережених раніше записів. Нова особа через сервіс/форму потребує явної статі. Основна форма редагування дозволяє внести стать старої особи.
- `NameDictionary`: тип `surname`/`name`/`patronymic`, явна стать, base_form, normalized_key, сім відмінків, is_verified, revision та точні системні UTC-позначки. Унікальність — тип + стать + нормалізований ключ. Однакове слово для двох статей — два окремі записи; підбір між статями заборонений.
- `PersonNameCases`: окремі форми конкретного person_name_id, тип, знімки основного слова/статі, nullable відмінки, is_verified, revision й UTC. Унікальна пара person_name_id/тип; видалення підтвердженого неактивного PersonName каскадно видаляє тільки його форми. Нова історична версія ПІБ не успадковує персональні форми старої.
- `NameDictionaryImport`: квитанція підтвердженого імпорту з унікальним ID, digest, режимом і системним часом. Це захист повторного запиту, а не повний Audit Log.
- `app/name_cases.py` — метадані трьох частин ПІБ, семи відмінків, статей та Excel-заголовків. `app/validators/name_cases.py` — явна валідація та нормалізований пошуковий ключ. Значення зберігаються з оригінальним регістром після NFC/strip; ключ додатково використовує casefold, нормалізовані апострофи/дефіси та пробіли.
- `app/repositories/name_case_repository.py` — ORM-доступ без commit/rollback. Сервіси `name_cases.py`, `person_registration.py`, `name_dictionary_import.py` — пріоритет форм, перевірки й транзакції. `app/routers/name_cases.py`, `admin.py`, `persons.py` — HTTP та шаблони. JS не виконує граматичних припущень.

Слова й форми: 1–100 символів, літери Unicode, апострофи, дефіси та внутрішні пробіли. Прізвище та ім'я обов'язкові, по батькові може бути відсутнє. Старе примусове capitalize та обмеження 3–25 замінено: регістр, апострофи й короткі імена на кшталт «Ян» зберігаються.

## Отримання та перевірка форм

`services/name_cases.resolve(db, person_name, sex)` повертає для кожної частини forms, sources, warnings і stale:

1. Непорожня персональна форма, якщо знімки слова/статі відповідають поточним.
2. Форма перевіреного словника для тієї самої статі й ключа.
3. NULL із попередженням. Називний також відомий без словника з основного поля PersonName.

Неперевірені персональні значення не приховуються, але мають попередження. Позначка is_verified ставиться лише після явної перевірки користувачем та за повного набору форм. Порожні відмінки зберігаються як NULL; невідома форма не замінюється називним. Збережені автоматично заповнені значення також є персональним знімком; подальше оновлення глобального словника їх не перезаписує. За потреби користувач явно застосовує новий словник.

Після виправлення основного ПІБ або статі старі знімки залишаються для перевірки, але resolver їх не застосовує. Споживачам форм слід викликати resolver, а не читати snapshot без перевірки його binding.

## Створення й редагування

`/persons/new`: спочатку тільки вибір статі, потім три основні поля ПІБ зі згортаними шістьма іншими відмінками, РНОКПП, чинний компонент неповної дати та звання з Rank. Пошук на blur використовує read-only `GET /name-dictionaries/lookup?kind=…&sex=…&word=…`.

`name_cases.js` зберігає ручну чернетку, binding слова/статі та номер запиту. Запізніла відповідь не змінює новіші значення. Ручні виправлення не замінюються без підтвердження. Зміна слова/статі показує stale-попередження і блокує збереження до очищення старих форм або їх явного повторного прийняття; приховані binding-поля повторно перевіряє сервер. Невідоме слово дає підказку ручного заповнення.

`person_registration.register_person` об'єднує ServicePersonCreate, PersonNameCases і наявний ServicePersonRankFunc у service_transaction: один commit або повний rollback. Вкладені сервіси отримують commit=False. Дата/номер наказу про початкове звання не вигадуються. Помилка зберігає всі поля форми, стать, звання, відмінки й часткову дату. Успіх переводить на `/persons/{id}/created` з двома діями: список людей або повна анкета.

Посилання «Відмінки» в історії ПІБ відкриває `/person_name/{person_name_id}/cases`. Це редагування персональних форм саме цього історичного запису; глобальний словник воно не змінює. Основне слово на цій сторінці тільки для читання; його коригує наявна форма ПІБ.

## Мінімальний адміністративний доступ

Повної системи користувачів/ролей у проєкті немає. `/admin` — окремий захищений розділ. Без PROJECT2_ADMIN_TOKEN або якщо він коротший за 32 символи адміністративні операції вимкнені (503). Паролі/токени в коді та БД не зберігаються.

Згенерувати секрет локально: `python -c "import secrets; print(secrets.token_urlsafe(32))"`. Задати його в оточенні процесу сервера, не комітити. Застосунок сам не завантажує .env.

Для Bash:

```sh
export PROJECT2_ADMIN_TOKEN='<власний згенерований секрет>'
export PROJECT2_ADMIN_ALLOW_HTTP=1
python -m uvicorn app.main:app --reload
```

Для PowerShell:

```powershell
$env:PROJECT2_ADMIN_TOKEN = '<власний згенерований секрет>'
$env:PROJECT2_ADMIN_ALLOW_HTTP = '1'
python -m uvicorn app.main:app --reload
```

ALLOW_HTTP=1 призначений лише для локальної розробки з localhost. У робочому розгортанні залишити його відсутнім, використовувати HTTPS. Після запуску відкрити `/admin/login` і ввести власний секрет. Сесія — підписана cookie на 8 годин, HttpOnly, SameSite=Strict, Path=/admin; на HTTPS також Secure. Зміна токена відкликає попередні сесії. Logout видаляє cookie. Усі адміністративні POST, крім самого входу, вимагають CSRF, прив'язаний до цієї сесії. Завантаження шаблону також вимагає адміністративного входу.

Це спільний адміністративний секрет без персональних ролей, ідентичності оператора та повного журналу. Публічний словниковий lookup тільки читає перевірені форми; він не дає права змінювати глобальні дані. Доступ до інших кадрових сторінок зберігає попередню політику застосунку.

## Точний формат Excel

Порожній файл у репозиторії: [templates/name_dictionaries_empty.xlsx](templates/name_dictionaries_empty.xlsx). Той самий формат генерує `/admin/dictionaries/template.xlsx`.

Три обов'язкові аркуші: `surnames`, `names`, `patronymics`. Кожен може бути порожнім; загалом потрібен принаймні один рядок даних. Інші аркуші не імпортуються. У першому рядку кожного аркуша **точно такі заголовки в такому порядку**:

| Колонка | Значення |
| --- | --- |
| base_form | Основне слово з правильним регістром. |
| sex | Тільки male або female; не визначається з ПІБ. |
| nominative | Називний; повинен точно дорівнювати base_form, включно з регістром. |
| genitive | Родовий. |
| dative | Давальний. |
| accusative | Знахідний. |
| instrumental | Орудний. |
| locative | Місцевий, без допоміжних приміток у дужках. |
| vocative | Кличний. |

Дані — з другого рядка, без пояснювальної другої строки. Усі дев'ять полів заповненого рядка обов'язкові: якщо відмінки невідомі, не імпортувати цей словниковий запис, доки їх не перевірено. Порожні рядки пропускаються. Формули, числові слова, помилки Excel, сторонні непорожні колонки, повтори нормалізованого ключа для тієї самої статі/словника відхиляються з аркушем і номером рядка. Два записи різної статі дозволені. Обмеження: .xlsx до 5 МБ, до 50 МБ після розпакування, до 10000 рядків даних за імпорт.

## Імпорт і ручне керування

1. `/admin`: вибрати файл та режим «тільки нові» або «додавання й оновлення».
2. Попередній перегляд перевіряє весь файл без запису. Показує всі форми, нові/оновлювані/незмінені/пропущені записи та помилки. У режимі add відмінний існуючий запис рахується пропущеним. Структурні помилки також входять до лічильника помилок.
3. Критична помилка забороняє весь імпорт. Без змін підтвердження не пропонується.
4. Для запису підтвердити перевірку всіх довідкових форм; за оновлень — ще окремий прапорець їх підтвердження. Автоматичного перезапису немає.
5. Підтвердження повторно читає revision під BEGIN IMMEDIATE через service_transaction(immediate=True). Зміна словника після preview відхиляє операцію. Рядки та квитанція імпорту зберігаються одним commit; помилка відкочує все.
6. Повтор того самого підтвердження блокує унікальна квитанція; повторне завантаження незмінних даних дає unchanged і не створює дублікати. Для свідомого пізнішого повернення попередніх форм потрібен новий preview у режимі update та явне підтвердження.

Preview-файли зберігаються у приватному системному tmp/project2-name-dictionary-previews (0600/0700), підпис діє 20 хвилин і прив'язаний до адміністративної сесії. Використано наявний механізм підпису з окремим purpose; після перезапуску без стабільного STAFF_SIGNING_KEY preview потрібно повторити. Вихідний Excel не зберігається. Прострочені файли прибираються при наступному preview.

`/admin/dictionaries` має пошук/перегляд по 50 рядків і ручне додавання/редагування одного запису з revision. Неперевірений запис не бере участі в автопідборі; для перевіреного потрібні всі сім явних форм. Зміна словника не торкається person_name_cases.

## Безпечне оновлення існуючої SQLite

Міграція явна, не виконується під час запуску сервера. Спочатку зупинити сервер та інші writer-процеси. З кореня, у вибраному Python-середовищі:

```sh
python -m app.database.migrate_name_cases --database data/database/project2.db
```

Команда вимагає наявну БД попередньої штатної архітектури: перевіряє таблиці/колонки, чинні тригери, integrity_check та foreign_key_check. Створює поряд узгоджену резервну копію `*.before-name-cases-*.sqlite3` (0600) через SQLite backup API. Під BEGIN IMMEDIATE додає nullable sex із CHECK та тільки три нові таблиці; старих таблиць не перебудовує і даних не видаляє. При DDL-помилці rollback скасовує всю зміну схеми; резервна копія залишається. Повторний запуск актуальної схеми нічого не змінює. Старі доштатні/неповні сторонні схеми відхиляються для окремої міграції.

Старим людям не підставляються стать, відмінки або звання. Наявна локальна/хмарна БД під час цієї реалізації не мігрувалася; перевірялися лише окремі тестові файли. Нову порожню БД як і раніше створює init_db. Міграція не змінює точність дат, UTC, PersonEvent, штатні періоди, призначення чи тригери їхніх правил.

Засівання нових тестових людей тепер вимагає в аркуші persons також **sex**, поряд із колишніми вісьмома колонками. Дозволені явні male/female; стать не вгадується. РНОКПП лишається ключем ідемпотентності, наявні люди не перезаписуються. Кореневий reference_data.xlsx автоматично не доповнювався: перед новим засіванням його треба заповнити цими даними. Граматичні словники seed не створює.

Окремий довідник майбутніх функціональних колонок — `app/service_basis.py`: contract → «за контрактом», mobilization → «за мобілізацією». Він не є словником ПІБ та не змінює PersonServiceHistory.

Перед змінами: 363 Python, 25 Node, 72 Chromium. Після: **399 Python passed**, **31 Node passed**, **82 Chromium-сценарії**, без pageerror; два попередні deprecation-попередження залежностей. Додатково повторено 10 нових браузерних сценаріїв після підсвічування помилок. Тести ізольовані: tmp_path SQLite/backup, окремий робочий каталог старих pytest-фікстур, Chromium на SQLite в пам'яті з випадковим тестовим секретом.

З кореня підготовленого середовища: `node --test tests/js/*.test.cjs` та `PYTHON=.venv/bin/python CHROMIUM_PATH=/usr/bin/chromium node tests/browser/column_visibility.cjs`. Для окремої перевірки — COLUMN_STAGE=name_cases. Python-набір — явний каталог tests/; у cloud його виконано з /tmp/project2-staff-tests з app-symlink і PYTHONPATH, щоб відносна project2_test.db не торкалася робочого каталогу.
