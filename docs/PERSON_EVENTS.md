# Події військовослужбовця

У `/person-positions` кнопка «Події» біля офіційно призначеної людини відкриває Bootstrap Modal: історію, створення й редагування. Вакантна посада не має цієї кнопки; Міраж не підміняє офіційного власника. Планування та підтвердження завершення додають два поля PersonEvent через Alembic 0002_event_completion; див. [EVENT_CONTROL.md](EVENT_CONTROL.md).

## Архітектура

- `routers/person_events.py`: GET `/persons/{person_id}/events`, POST за тією самою адресою, POST `/persons/{person_id}/events/{event_id}`. HTTP-адаптер не виконує ORM-запитів; POST перевіряє Origin чинним механізмом.
- `services/person_events.py`: контракт редактора, каталог типів/підтипів, серіалізація періодів, повні ISO-дати вебформи → Python Date, перевірка власника та відбитка збереженого стану при редагуванні. Не замінює PersonEventService.
- `services/service_for_person_event.py`: чинний PersonEventService; точні дати, тривалість, належність/активність довідників, конфлікти та автоматичне завершення попередньої події. Старі виклики через session_factory і зовнішнє db= збережені.
- `repositories/event_repository.py`: включні SQL-умови перетину, вибірки та запис без commit. Строгі `<`/`>` виправлені на `<=`/`>=`; одноденна вибірка тепер враховує обидві межі.
- `components/person_events.html`, `static/js/person_events.js`: одне модальне вікно, асинхронні запити, залежний підтип, безпечний текстовий рендеринг, фокус/підсвічування помилок. Обробник кнопок делегований і працює після переставляння колонок.

Подія завжди належить Person через person_id, без FK до Position/StaffVersion. Переведення або зміна версії не змінює її реквізити. `assignment_events.py` й надалі читає історичні посади окремо, позначаючи невідомі періоди.

## Дати та конфлікти

Усі date_start/date_end/order_date/planned_end — повні календарні Date; date_start обов'язкова. Неповні дати відхиляються. Системний час і UTC-політика не змінені.

- Відкритий запис: date_end=NULL, duration=NULL. Показ: «ДД.ММ.РРРР — по сьогодні», без запису сьогоднішньої дати під час читання.
- Якщо завершення вказане, duration обчислюється включно: end − start + 1. Якщо зазначено також duration, вона повинна збігатися. Додатна duration без завершення, як і раніше, дозволяє обчислити точне завершення.
- Спільний граничний день — конфлікт; наступний день після завершення дозволений. Відкритий інтервал необмежений зверху.
- Тільки **створення фактичної** нової події може завершити одну попередню відкриту SERVICE/DUTY/DAY_OFF з ранішим початком: previous.end=new.start−1, duration перераховується. Новий фактичний запис може бути відкритим або завершеним. Відпустка, лікування, відрядження та невідомі типи автоматично не завершуються; майбутній план не завершує жодної поточної події.
- Завершені записи не розбиваються й не переписуються. Два відкриті кандидати, рівний/пізніший початок відкритої події, будь-які додаткові перетини нового або запропонованого попереднього періоду дають конфлікт без запису. Перевіряються всі конфлікти, а не лише перший.
- Редагування зберігає event_id, виключає його зі списку конфліктів та не завершує інші події автоматично.

Коди, назви, колір, активність і exclusive читаються з наявних EventType/EventSubtype. Нові записи приймають лише активні значення; старе неактивне значення власної події можна зберегти при історичному виправленні. Підтип завжди має належати типу; зміна типу скидає несумісний вибір. Ознака exclusive збережена як метадані, але не вводить неузгоджених винятків із погодженого загального правила перетинів.

## Транзакції й конкурентність

Вебоперація володіє одним `service_transaction(immediate=True)`, вкладені event-виклики з db= не роблять commit/rollback/close. PostgreSQL бере FOR UPDATE на Person **до** перевірки конфліктів і запису; редагування далі блокує конкретний PersonEvent у тому самому порядку. Незалежні люди не блокують одна одну. SQLite BEGIN IMMEDIATE залишається тільки legacy-адаптером.

Закриття попередньої і INSERT нової — одна транзакція. Помилка INSERT, конфлікт або відмова валідації відкочує всю вебоперацію. Відбиток полів expected_state запобігає непомітному перезапису застарілої форми без додавання фіктивної revision-колонки. Це перевірка актуальності, не авторизаційний токен.

Конфлікт повертає HTTP 409 і список подій із назвами та періодами. Помилка поля — 422 із field; незмінений старий сервісний контракт може повернути список ORM-конфліктів. Зовнішній власник db= зобов'язаний rollback при помилці всієї своєї операції.

## Інтерфейс та межі

Помилки дат, конфлікти й мережева відмова не очищують поля, не закривають редактор і не перезавантажують штатку. Список можна оновити без втрати чернетки. Після успіху перечитується історія й показується повідомлення. Фільтри, URL, пресети, копіювання, призначення та Undo/Redo штатки не змінюються.

Нові event API використовують чинну політику доступу кадрових/staff-операцій; загальносистемний ACL цим завданням не запроваджено. Production-обмеження з [POSTGRESQL_SETUP.md](POSTGRESQL_SETUP.md) залишаються. Захист перетинів працює в сервісних операціях через спільне блокування Person; довільний прямий SQL не отримав нового exclusion constraint. Фізичне видалення подій заборонене; доступне анулювання зі збереженням реквізитів/історії. Редактор довідників та нові типи не додавалися; календар і планування тепер описані в EVENT_VIEWS/EVENT_CONTROL. Нативні поля дати використовують уже підтримувані точні значення.

## Журнал і кнопки правої панелі

Редактор повторно використовується журналом /events через `PersonEvents.open(personId,label,{eventId,create})`. Після успіху DOM-подія `person-events:saved` оновлює журнал і значок штатки. Запис/конфлікти/expected_state не дублюються в нових представленнях. Опис матриці та стану на дату — [EVENT_VIEWS.md](EVENT_VIEWS.md).

## Орієнтовний строк і підтвердження

`planned_end` не змінює фактичні date_end/duration. Прапорець completion_confirmed та дія повернення використовують чинний edit endpoint, expected_state і ту саму транзакцію. Майбутні дати відображаються як міражі незалежно від PersonPositionMirage. Реєстр SERVICE-підтипів розширено без зміни старих DUTY/DAY_OFF. Усі поля дат Modal тепер маскуються ProfileDates як ДД.ММ.РРРР зі збереженням canonical ISO. Міграція, сумісність старих викликів і правила контролю — [EVENT_CONTROL.md](EVENT_CONTROL.md).

## Виправлення типу й анулювання

Edit підтримує confirm_type_change; без явного прапорця зміна event_type_id відхиляється core-сервісом. Знімки PersonEventCorrection записуються атомарно. POST /persons/{person_id}/events/{event_id}/annul приймає причину/expected_state та зберігає лише метадані анулювання й аудит. Архів readonly, UPDATE/DELETE історії та фізичне видалення подій заборонені БД. Доступний справжній автор визначається з персональної cookie-сесії, без неї NULL. Нової системи прав не введено. Деталі — [EVENT_CORRECTIONS.md](EVENT_CORRECTIONS.md).
