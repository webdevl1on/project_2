# Версії штатів та історичні призначення

Реалізація `testing`. Джерело істини призначень — **PersonAssignment**; поточний стан обчислюється за фактичними датами. Структура/версія/посада не визначають власника події PersonEvent.

## Схема

| Сутність | Поля та правила |
| --- | --- |
| StaffStructure / staff_structures | id, унікальний code, name, created_at/updated_at UTC, revision; групує версії одного штату. |
| StaffVersion / staff_versions | id, staff_structure_id, name, valid_from Date, valid_to Date NULL, унікальний import_key, системні UTC-поля, revision. Назва унікальна в межах структури, періоди не перетинаються. |
| Position / positions | Чинні реквізити й відмінки, staff_version_id, системні UTC-поля, revision. Унікальна пара (staff_version_id, position_number); однаковий номер у різних версіях дозволено. |
| PersonAssignment / person_assignments | id, person_id, staff_position_id, assigned_from Date, assigned_to Date NULL, системні UTC-поля, revision. Обмеження перетинів за людиною й посадою, без глобального unique person_id. |
| PersonPosition | Лише застарілий Python-alias PersonAssignment для сумісності імпортів; фізичної person_positions немає. person_position_id/position_id — синоніми id/staff_position_id того самого запису, не друга копія даних. |
| PersonEvent | Наявний FK person_id; Date date_start обов’язковий, date_end/order_date — точні або NULL за чинними правилами. Історія посад не змінює подію. |

`Person.positions` і `Position.persons` тепер колекції історичних PersonAssignment, а не готова вибірка поточного стану. Поточність визначають `assignments_at(db, on)` та вибірка таблиці. Новий SystemTimestamps використовує точні DateTime/default/onupdate datetime.now(UTC) і revision SQLAlchemy; `HistoryModel`, його is_active та політика naive UTC у SQLite не змінені. Для кадрової історії немає окремого прапорця активності чи is_free. Прапорець «Поточна» під час імпорту задає відкритий кінець і перевіряє, що початок не в майбутньому; це не друге джерело поточності.

## Періоди та цілісність

- Межі включені: 01.01–31.05, наступна версія — з 01.06. Невідомий кінець — NULL; невідомий початок не допускається і не підставляється автоматично.
- Призначення цілком належить періоду версії; у скінченної версії призначення не може мати відкритий кінець.
- Людина не займає дві посади одночасно навіть у різних структурах/версіях. Одна посада не має двох людей одночасно. Перевіряється вся історія, а не останній створений запис.
- Прогалини версій/призначень дозволені. При відсутності актуальної версії таблиця порожня, а не підмінена останньою створеною версією.
- SQLite foreign_keys увімкнені для всіх SQLAlchemy SQLite-підключень. Індекси, CHECK і тригери захищають періоди/календар, перетини й межі версій навіть для raw SQL. Фізичне видалення історичних призначень, версій і посад заборонене тригерами; змінювати версію наявної посади не можна.
- `write_unit` починає BEGIN IMMEDIATE до повторної перевірки стану, завершує операцію одним commit або rollback. Незбережені зміни стороннього виклику не відкидаються: сервіс відмовляє до початку операції. Після початкової read-only роботи сесія звільняє стару транзакцію й повторно читає стан під блокуванням.
- SQLite має одного writer. Змагання двох окремих підключень перевірене тестом; програвший отримує конфлікт без втрати попередніх призначень. Блокування/помилка не вважається успіхом; навантажувального тесту великих баз немає.

SQL-вибірки історії, періодів та зайнятості винесено до `app/repositories/staff_repository.py`; StaffService зберігає кадрові рішення, revision і незмінний write_unit. `staff_read.py` готує читання сторінок без HTTP/HTML, а `app/templating.py` усуває імпорт templates між роутерами. Спільні правила життєвого циклу сесій — у [ARCHITECTURE.md](ARCHITECTURE.md#єдині-правила-транзакцій).

## Кадрові операції та виправлення

`app/services/staff_service.py`:

- `create_assignment` — явний історичний або майбутній період; жодних дат із created_at.
- `correct_assignment` — виправлення того самого запису, з revision і повною перевіркою всіх конфліктів; фіктивного переміщення не створює.
- `correct_position` — перевірене виправлення реквізитів конкретного Position; інші версії й посади не змінюються.
- `correct_version` — виправлення назви/меж, яке не може зробити наявні призначення недопустимими.
- `close_version` — явне підтверджене закриття. Всі відкриті або пізніші завершення призначень обмежуються обраною датою в одній транзакції; якщо є призначення з початком після неї — вся операція відхиляється. Люди нікуди не переносяться.
- `assign` — перевірка підписаного знімка, зайнятості, версії, дат і revision. При переведенні попередній запис завершується днем перед новим початком, новий починається явною датою. Зайнята іншою людиною ціль не звільняється автоматично. Повтор тієї самої посади не створює запису. Початок і завершення в один день забороняють ще одне переміщення того самого дня: для помилки є окреме виправлення історії.

Виправлення зберігає ідентичність історичного запису, але не є Audit Log старих і нових значень; універсальний Audit Log відкладений. Ручне виправлення історичної назви посади свідомо змінить її відображення для пов’язаних подій; наступний імпорт сам цього не робить.

## Інтерфейс

`/person-positions` має вибір версії та «Стан на дату», кнопку «Завантажити штатну структуру» і посилання `/staff/history`. При перемиканні версії дата перегляду приводиться до її відомих меж; дату кадрової операції видно окремо у формі. Сортування/фільтри/URL включають version_id та as_of. Каталог 54 полів, стабільні ключі, пресети, DnD, ширини, копіювання виключно кнопкою, приховування та Undo/Redo вигляду збережені. Undo вигляду не скасовує кадрові зміни і не перемикає версію штату.

`person_picker.html`, `person_picker.js`, `person_picker.css` — багаторазовий dropdown із пошуком по ПІБ/відображуваній даті; дані готує `person_picker.py` bulk-запитом за чинним правилом ПІБ/звання. Кожна особа має три рядки: ПІБ; звання й дата; статус із номером посади. Вільні — першими, далі ПІБ без урахування регістру. Повні тезки отримують додатковий технічний код запису; РНОКПП/паспорт не показуються. Внутрішній ID залишається hidden-значенням. Історичні форми позначають, що статус у списку наведений на сьогодні; фактичні історичні конфлікти перевіряє сервер.

`staff_assignments.js` робить prepare перед записом і показує Bootstrap Modal для переведення/звільнення. «Ні» не виконує запису. «Так» надсилає підписаний знімок актуального джерела/цілі/версії/дати; після зміни даних потрібна нова перевірка. Для вільної людини запис виконується після «Зберегти». Є повідомлення перевірки/помилок; повторні запити не можуть створити дубль.

`/staff/history` надає явне закриття, виправлення версії/посади/призначення та додавання історичного призначення. Наявну службову історію PersonServiceHistory не підмінено історією штатних призначень.

## Помилки форм історії

Причина попереднього скидання — звичайний HTML POST і перехід на staff_error.html при ValueError; значення не поверталися у вихідну форму. На /staff/history підключено staff_history_forms.js: він перехоплює лише POST-форми цієї сторінки та надсилає FormData через fetch із Accept: application/json. Form_failure повертає detail і fields, звичайний HTML fallback збережений.

Помилки не замінюють DOM, не скидають person picker/посаду/дати/чернетки й не закривають details. Є локальна перевірка обов’язкових полів, вибору людини, порядку дат і додатного номера посади; серверні перевірки календаря, періодів, revision та унікальності залишаються обов’язковими й незмінними. Номер із початковими нулями допускається, як і на сервері.

Повідомлення біля конкретної форми має role=alert; поля позначаються aria-invalid/is-invalid, aria-describedby та контуром Bootstrap danger. Фокус переходить до помилкового поля або до повідомлення, якщо помилка стосується всього запису. Повторний номер посади/назва версії/код структури пояснюються без SQL-тексту. Обробляються FastAPI 422, конфлікти 409, неочікувана відповідь і збій мережі. Під час запиту блокується повторне надсилання; після відмови можна виправляти й повторювати, зберігши введене. При невідомому мережевому результаті показується прохання перевірити результат перед повтором.

Після успіху виконується навігація на повернену сервером сторінку: користувач бачить актуальні дані, revision і повідомлення про успіх. Автоматичне збереження чернеток у localStorage не додано; безперервність при помилці забезпечує збереження поточного DOM, а не окреме сховище. SQLAlchemy-моделі й бізнес-сервіси цього виправлення не змінювалися.

Перевірки виправлення: **342 Python passed**, **25 Node passed**, **10 Chromium-сценаріїв пройшли** (5 нових history_forms і 5 наявних staff); два наявні deprecation-попередження Python. Нові сценарії перевіряють створення/редагування призначення, неправильні дати, серверний перетин/застарілий запис, збій мережі, чернетки версії/посади, підсвічування/фокус, відсутність навігації на помилках і успішне виправлення. Повний браузерний набір на цьому етапі не повторювався. Окремий запуск — COLUMN_STAGE=history_forms.

## Excel: перевірка → підтвердження

Маршрути `/staff/import/preview` та `/staff/import/confirm`, сервіс `staff_import.py`:

1. Файл .xlsx до 5 МБ, до 50 МБ розпакованих даних. Тільки positions, ті самі 11 заголовків, та сама пояснювальна друга строка, дані з третьої. Обов’язкові колонки, заповнені реквізити, позитивні номери й дублікати перевіряються до запису. Повністю порожні рядки пропускаються.
2. Підрозділ — чинний unit_short у рядку посади; окремої ієрархії/ID підрозділів у форматі немає. Кількість — число унікальних нормалізованих unit_short, про це є попередження. Інші аркуші не читаються для імпорту сутностей.
3. Для архівної версії обидві дати обов’язкові; для «Поточна» — початок та порожнє завершення. Перетин із попередньою версією дає помилку й посилання на її явне закриття.
4. Попередній екран показує назву, період, кількість посад/підрозділів, помилки по рядках і попередження. За критичних помилок кнопки підтвердження немає. До підтвердження StaffStructure/StaffVersion/Position не створюються.
5. Підтвердження повторно перевіряє поточні періоди та створює версію і всі посади в одній транзакції. import_key унікальний; повтор того самого запиту або повторний імпорт конфліктних даних не перезаписує історію.
6. Нова версія завжди вакантна; старі призначення/посади/версії не змінюються. Після успіху відкривається таблиця нової версії.

Підготовлені рядки зберігаються тимчасово у каталозі project2-staff-previews системного tmp (файли 0600, каталог 0700); вихідний Excel не зберігається. Підписані підтвердження діють 20 хвилин, старі preview-файли прибираються при наступному завантаженні. `STAFF_SIGNING_KEY` задається через оточення для стабільності між перезапусками/кількома workers; без нього використовується випадковий ключ одного процесу й після перезапуску перевірку потрібно повторити. Не записувати секрет у репозиторій. Це не механізм авторизації кадрових дій; повної системи користувачів/ролей немає. Нове адміністрування словників має окремий токенний доступ, описаний у [NAME_CASES.md](NAME_CASES.md).

## Події та точність дат

`assignment_events.py` надає `events_for_people` незалежно від наявності призначень, `events_for_staff` для людей на вибраній структурі та `event_positions` для всіх посад протягом події. Результат містить історичні назви/номери/версії, окрему власну note та unknown_periods. Відсутність/прогалини позначаються явно. Для відкритої події можна передати кінець вікна перегляду, не записуючи його як кінець події. Календарний UI не створено.

PersonEvent зберігає SQL Date; ORM та SQLite відхиляють неповні/неможливі дати й кінець перед початком. NULL date_end залишається для відкритої події; чинний розрахунок повного завершення за тривалістю не змінений. Мінімально виправлено чинний сервіс подій: перевірка людини через наявний ServicePersonCheck, збереження підготовлених полів, закриття сесії, виключення редагованої події з конфліктів, select замість db.select. Це дозволяє створення/редагування подій заднім числом без призначень; часткові дати не приймаються. Після архітектурного рефакторингу SQL подій/історичних посад виконується через EventRepository/StaffRepository. Усі операції PersonEventService підтримують зовнішнє db= без commit/rollback/close; сумісні окремі виклики через session_factory збережено. Помилка спільної операції має спричиняти rollback у зовнішнього власника транзакції; конфлікт створення/редагування, як раніше, повертає список подій без запису.

## БД та команди

Автоматичних міграцій/перенесення старих призначень немає: невідомі минулі дати не вигадуються. require_current_schema перевіряє таблиці, колонки, тригери та відсутність застарілої фізичної person_positions. Наявний файл автоматично не видаляється. init_db отримує нову схему й тригери через реєстр моделей; його захист існуючих файлів незмінний.

З кореня репозиторію, у підготовленому Python-середовищі, для **нової окремої** SQLite:

```sh
python -m app.database.init_db --database data/database/staff_check.sqlite3
python -m app.seeds.seed_structure --database data/database/staff_check.sqlite3
python -m app.services.seed_test_people --database data/database/staff_check.sqlite3
```

Без параметрів версії seed_structure засіває лише типи/підтипи подій і звання. Тестові люди — окремо, без призначень. Для CLI-імпорту штату додати явні --version-name, --valid-from (ISO), необов’язкову --valid-to, --structure-code та --excel. Повтор того самого seed з ідентичними даними не створює дубль; відмінні дані вже існуючої версії дають помилку.

Для **ручного пересоздання основної** SQLite спочатку зупинити сервер і закрити всі підключення. Перша команда нижче видаляє дані саме вибраної БД:

```sh
python -m app.database.init_db --database data/database/project2.db --recreate
python -m app.seeds.seed_structure --database data/database/project2.db
python -m app.services.seed_test_people --database data/database/project2.db
python -m uvicorn app.main:app --reload
```

Потім відкрити /person-positions → «Завантажити штатну структуру», вказати фактичні назву й дати, перевірити та підтвердити імпорт. Штат навмисно не створюється з вигаданим періодом. Наведені команди пересоздання основної БД в цьому завданні не виконувалися.

## Перевірки

- Повний pytest: **341 passed**, два попередні deprecation-попередження Starlette/httpx та AnyIO. Старі регресії використовують явні синтетичні періоди з tests/staff_fixtures.py; runtime-моделі таких default-дат не мають. Новий test_staff_history.py працює без цієї сумісності.
- Node: **25 passed**. Chromium: **67 сценаріїв пройшли** (попередні 62 і п’ять нових staff-сценаріїв), без pageerror. Окремий запуск: COLUMN_STAGE=staff.
- Тест конкурентних операцій — два Session/підключення й окрема файлова SQLite; тільки одне конкуруюче призначення успішне. Тести перевіряють також DB-тригери, відмову прямого видалення історії, rollback після збою вставки, stale-підтвердження, виправлення та точні дати подій.
- CLI на кореневому Excel в окремій тимчасовій SQLite двічі залишив 1 синтетичну версію, 10 посад, 15 людей і 0 призначень. Існуючі робочі SQLite не пересоздавалися. Тестовий браузерний reset діє лише на його SQLite в пам’яті й не реєструється у робочому застосунку.
- Навантажувальні тести/інші браузери, перенесення старої БД, повна календарна візуалізація та Audit Log не реалізовані. Історичні виправлення змінюють запис на місці; для зберігання всіх попередніх значень потрібен майбутній Audit Log.
