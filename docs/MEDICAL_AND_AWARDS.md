# ВЛК, поранення, нагородження, ДНК і завдання

Актуальний режим: **авторизацію тимчасово вимкнено за замовчуванням для всього застосунку**, включно з admin, медичними та документальними API. Вхід, токени, CSRF та обмеження localhost у цьому режимі не потрібні. Наведені нижче правила захищеного/локального режимів збережені для майбутнього й діють після явного `PROJECT2_AUTH_ENABLED=1`.

Реалізація: `routers/medical.py` → `services/medical.py` → `repositories/medical_repository.py` → ORM. Словники стабільних кодів, українські назви, метадані форм і категорії документів — `app/medical_catalog.py`. Призначення, незалежна історія служби, PersonEvent та HistoryModel не змінені. Немає генетичних або біометричних даних.

## Таблиці та зв’язки

Усі нові таблиці описані в `app/models/medical.py`.

| Таблиця / модель | Призначення |
| --- | --- |
| person_medical_exams / MedicalExam | Багато ВЛК на Person: стан, підстава/опис, необов’язковий injury_id, запланована дата, точна дата довідки, номер 150, установа 1000, діагноз 2000, придатність. Окремої «дати комісії» немає. |
| person_injuries / Injury | Незалежні поранення: точні nullable дати поранення/довідки, опис 200, район 1000, обставини 2000, номер 150, exam_not_needed. |
| person_awards / Award | Незалежні нагородження, nullable injury_id, стан, реквізити й окреме підтвердження фактичного подання/оформлення рапорту, причина недоцільності, реквізити результату. |
| person_dna_samples / DnaSample | Історія здач: конверт 150, обов’язкова точна collected_on, частина зберігання 250. |
| person_medical_selections / MedicalSelection | PK person_id, nullable exam_id та revision ручного вибору. NULL означає автоматичний режим. Немає копії придатності. |
| personnel_tasks / PersonnelTask | Розширюваний kind, Person, необов’язкові Injury/Award, назва, відповідальні відомості, примітка, статус, manual_decision та причина рішення. |
| medical_document_links / MedicalDocumentLink | PersonDocument → рівно один із MedicalExam/Injury/Award, категорія; один документ може бути явно пов’язаний із кількома фактами тієї ж особи. |
| personnel_audit / PersonnelAudit | Незмінний журнал предметних змін: Person, реальний User, точний UTC, вид/ID сутності, операція, old/new. |

Предметні записи, вибір і зв’язки використовують чинний SystemTimestamps/revision. Нові дати зберігаються як Date; задані значення завжди повні. Відомості можуть бути відсутніми: зокрема поранення й незавершене ВЛК зберігаються без дат або файлів. Невідомі компоненти не підставляються. Завершене ВЛК без дати довідки дозволено як неповний обліковий запис, але воно створює неоднозначність автоматичного вибору. Завершений стан сам по собі не потребує необов’язкових номера/установи/діагнозу/копій.

Сервіс і SQL-тригери перевіряють належність пов’язаних записів одній особі; тригери також захищають календар і довжини. Є unique partial index автоматичного завдання на injury_id. Журнал append-only. Фізичного видалення фактів через API немає.

## ВЛК і активна довідка

Стани: NEEDS_EXAM, PLANNED, COMPLETED. Перші два входять до контрольного списку непроведених; COMPLETED виключається незалежно від необов’язкових реквізитів. Підстави INJURY / ILLNESS / OTHER; посилання на поранення дозволено тільки з INJURY, але не є обов’язковим. Повторна комісія — новий запис. exam_not_needed у пораненні встановлюється явним рішенням у завданні injury_vlk (опис нижче); воно не створює й не видаляє ВЛК.

Придатність: FIT — «Придатний», FIT_SUPPORT — «Придатний до служби в тилових частинах забезпечення», UNFIT — «Непридатний». Словник FITNESS використовується формами, оглядом і каталогом/фільтрами. Незавершене ВЛК не містить результату придатності.

`active_exam_selection()` — єдина SQL-проєкція вибору, `active_exam()` — сервіс її читання. Їх використовують анкета, штатка й доступні майбутнім генераторам документів. Спочатку береться явно вибраний завершений запис. Інакше обирається єдина найновіша дата серед завершених записів, лише якщо всі вони датовані. Однакові найновіші або відсутні дати дають порожнє значення й попередження. Заплановані/непройдені не беруть участі. Ручний вибір зберігається після додавання новішої довідки; можна повернути автоматичний режим. Для зміни вручну вибраного ВЛК на незавершене спочатку потрібно скасувати ручний вибір.

## Нагородження та завдання

Стани нагородження: NOT_PROCESSED, SUBMITTED, WAITING, AWARDED, NOT_APPROPRIATE. Статус не є підтвердженням дії.

За кожним Injury атомарно створюється одне завдання kind=injury_award «Опрацювати питання нагородження», навіть за відсутності ВЛК/нагородження/копій. Повторне редагування не дублює завдання й не створює нагороджень.

Автоматичне виконання потребує пов’язаного Award із одним із двох фактів:

- submission_confirmed=true, точна submission_on і непорожні submission_number;
- refusal_confirmed=true, точна refusal_on, refusal_number і коротка refusal_reason.

Це явне твердження уповноваженого користувача з персональним аудитом. Сам файл або вибір статусу не підміняють його; наявність копії не є умовою. У разі виправлення/скасування підтвердження автоматичне завдання знову відкривається з аудитом. Єдине підтверджувальне нагородження стає прямим award_id завдання; за кількох підтверджувальних записів довільний не обирається, всі доступні через поранення. Зміна подальшого статусу й часткове API-оновлення зберігають первісні реквізити, якщо користувач не змінює їх явно.

Ручні завдання допускають будь-яку кадрову тему й необов’язкові зв’язки. OPEN / COMPLETED / CANCELLED; ручне завершення або скасування потребує причини. Ручне рішення не переписується автоматикою. При конфлікті з автоматичним станом з’являється попередження; у контрольному розділі видно наявність ручного рішення. Зміна лише примітки/відповідальних відомостей автоматичного завдання не вимикає синхронізацію. Джерело автоматичного завдання не можна підмінити.

## Документи й доступ

Використовуються **чинні** PersonDocument, DocumentDetails, DocumentFile, DocumentAudit, DocumentStorage та захищені endpoints файлів із [DOCUMENTS.md](DOCUMENTS.md). Нового сховища/сесій/паролів немає.

Категорії поранення: form100, combat_certificate, circumstances, discharge. Для ВЛК: certificate, recommendation, discharge, other. Для нагородження: submission, refusal_report, award_order, other. На одну категорію дозволено кілька записів документів і кілька копій кожного. Документ можна прив’язати за ID або створити порожню оболонку типу other в одній транзакції зі зв’язком та аудитом. Створені предметні оболонки мають is_current=false: вони не займають єдиний загальний поточний слот типу other, зберігаються й відображаються через предметні зв’язки. Це не твердження про фізичну наявність або комплектність.

Реквізити ВЛК/поранення/нагородження не копіюються до DocumentDetails. Існуючий медичний документ може передувати ВЛК й залишатися незалежним. Файли — PDF/JPEG/PNG, до 10 МБ кожен, без обмеження кількості. Зберігання/підписи/вилучення/історія/компенсація звичайних помилок — чинні. Посилання видає захищене завантаження attachment, не PDF.js або inline-viewer. Відсутність файла не блокує предметний запис.

API `/persons/{person_id}/medical` і предметний аудит потребують персональної сесії. Viewer читає, editor/admin змінюють, write потребує CSRF. Dev-admin bypass не діє. Автор не приймається з payload. Вкладки мають невеликий GUI входу через існуючий /auth/login; локальний HTTP потребує явного PROJECT2_AUTH_ALLOW_LOCAL_HTTP=1, без скасування входу/CSRF. Старі кадрові сторінки й таблиця залишаються на попередній політиці доступу; глобальні ACL є окремим етапом. Стандартні права файлів та системного аудиту не розширені.

## API, інтерфейс і таблиці

- GET базового URL: факти, активне ВЛК/попередження, вибір/revision, зв’язки/файли, непройдені ВЛК, аудит.
- POST /exams, /injuries, /awards, /dna, /tasks: fields.
- POST /{kind}/{id}: fields + revision; часткові зміни зберігають інші реквізити.
- POST /active: exam_id або null, revision вибору.
- POST /{kind}/{id}/documents: category, revision факту, необов’язковий document_id.
- Файли завантажуються/вилучаються/читаються через існуючий документальний API.

Усі записи виконуються через service_transaction(immediate=True), один commit для факту/автоматичного завдання/аудиту або rollback. Репозиторій не володіє commit. Revision захищає редактори й ручний вибір. SQL-помилки не показують персональні значення запиту.

Анкета має окремі вкладки ВЛК, Поранення, Нагородження, ДНК та Проблемні питання / Завдання. Доступні історія, створення/редагування, ручне/автоматичне активне ВЛК, пов’язані записи й документи, завантаження/вилучення копій, журнал. Помилка сервера залишає форму та введені значення; відкриті блоки документів зберігаються при успішному оновленні. Огляд показує поточну придатність, не результат незавершеного ВЛК.

Каталог розширено з 55 до **76 інформаційних полів** (78 із двома службовими). 21 нове поле типово приховане: п’ять активного ВЛК; лічильники непройдених/запланованих/потрібних ВЛК; кількість/остання дата поранень; кількість нагороджень і п’ять лічильників станів; відкриті завдання; кількість здач ДНК, остання дата, конверт і частина зберігання. Для однакової останньої дати ДНК конверт/частина не обираються довільно.

`repositories/medical_table.py` містить довірені агрегатні SQL-проєкції; активне ВЛК outerjoin через максимум один chosen_id. Немає множення штатних рядків або запитів на кожного рядка. Вакансії показують «-», кількість відсутніх записів призначеної людини — 0. Чинні видимість/порядок/фільтри/сортування/пресети/копіювання/Undo не замінені. Точні дати використовують існуючий DateBinding.exact та форматування, allow_partial=false; компонентне меню не робить збережену дату неповною.

## Явна міграція

Робочу БД не мігрували, не видаляли й не засівали. Для наявної актуальної схеми документів, із зупиненим сервером/SQLite-клієнтами:

```sh
python -m app.database.migrate_medical --database data/database/project2.db
```

Maintenance lease, перевірки попередньої схеми/тригерів, integrity/FK; приватний SQLite backup `*.before-medical-UTC-RANDOM.sqlite3`; BEGIN IMMEDIATE; лише вісім нових таблиць/індекси/guards. Немає автоматичного створення предметних фактів, перенесення діагнозів із тексту, облікових записів чи зміни призначень. Повторний запуск — no-op; часткова невідома схема відхиляється, DDL-помилка має rollback. Старі міграції пропускають майбутні таблиці цього модуля, щоб зберігати власні попередні контракти.

Для окремої **нової** тестової БД також придатний init_db, який відмовляється перезаписувати наявний файл:

```sh
python -m app.database.init_db --database data/database/medical_check.sqlite3
python -m app.seeds.seed_structure --database data/database/medical_check.sqlite3
python -m app.services.seed_test_people --database data/database/medical_check.sqlite3
```

Персонального адміністратора створюють чинним bootstrap_account; команду й правила наведено в DOCUMENTS.md. Зміна БД не виконується при startup. Backup робочої системи має охоплювати SQLite й приватні файли.

## Локальна розробка без входу

Окремий PROJECT2_DEV_AUTH_BYPASS=1 підтримується через чинний current_user; підготовка тестової БД/реального editor-автора та PowerShell-команди описані в [DOCUMENTS.md](DOCUMENTS.md#локальний-тестовий-режим-без-введення-пароля). Дані вкладок завантажуються без логіна; видно попередження про режим розробки. Write зберігає CSRF і реального автора. Режим недоступний через LAN, proxy або чужий Origin, не створює облікових записів через HTTP і не змінює моделі/кадрові правила/синхронізацію завдань.

У типовому відкритому режимі усі вкладки відразу завантажуються через чинні API без входу/CSRF. UI показує «Авторизацію тимчасово вимкнено — вільний доступ». Правила активного ВЛК, фактів нагородження, автоматичних завдань і файлів незмінні; замість персонального автора використовується спільний службовий User. Попередній персональний і локальний dev-режими залишені для PROJECT2_AUTH_ENABLED=1.

## ВЛК після поранення: спочатку рішення

Нове поранення атомарно створює **два різні** завдання: чинне injury_award та окреме injury_vlk «Визначити необхідність проходження ВЛК за пораненням №…». Нового MedicalExam при цьому немає. Реєстратор не визначає потребу ВЛК: checkbox exam_not_needed прибрано із загальної форми/API збереження поранення. False не означає рішення «потребує».

injury_vlk використовує чинний PersonnelTask, Injury.exam_not_needed і зв’язки MedicalExam.injury_id. Колонка етапу/дубльована придатність не додаються. Сервер обчислює stage/stage_label та exam_ids:

- WAITING_DECISION — немає рішення та пов’язаних ВЛК;
- WAITING_EXAM — є NEEDS_EXAM/PLANNED, немає завершеного;
- EXAM_COMPLETED — є хоча б одне пов’язане COMPLETED;
- NOT_NEEDED — явний Injury.exam_not_needed=true; має пріоритет над автоматичним перерахунком.

Дві перші стадії OPEN, дві останні COMPLETED. Створення/редагування/переприв’язування ВЛК перераховує завдання всіх поранень цієї людини в тій самій транзакції. Повторні ВЛК окремі, але завдання одне. Втрата останнього завершеного ВЛК знову відкриває автоматичне завдання. Правила активної довідки не змінено.

Явна дія `POST /persons/{person_id}/medical/tasks/{id}/vlk-decision` приймає action=not_needed/reopen, непорожню reason та актуальну revision завдання. not_needed атомарно встановлює Injury.exam_not_needed, завершує task і зберігає причину в його decision_reason; обидва записи журналюються з автором. Скасування через reopen очищає позначку/ручне рішення й перераховує статус за фактами. Якщо вже є завершене ВЛК, результат після скасування лишається завершеним за фактом проходження; нова довідка або нове поранення не вигадуються. Причина скасування залишається в аудиті. Рішення не переписується звичайним редагуванням поранення або автоматикою. Універсальний редактор завдань дозволяє уточнити назву/відповідальні відомості/примітку, але не підмінити рішення ВЛК чи його джерело.

«Відкрити ВЛК» тільки відкриває чинний редактор із INJURY, правильним injury_id і NEEDS_EXAM; запис створюється лише після «Зберегти». Вкладка завдань типово показує OPEN; checkbox історії показує завершені/скасовані. Завершене завдання й причина доступні через історію та посилання з поранення. Старі exam_not_needed=true зберігаються: при подальшому збереженні пов’язаних фактів завдання відтворюється завершеним, відсутня стара причина не вигадується (UI повідомляє, що її раніше не зазначено).

### Адитивний індекс

До PersonnelTask додано лише partial unique index one_injury_vlk_task на injury_id для kind='injury_vlk'. Для **наявної** БД після зупинки сервера:

```sh
python -m app.database.migrate_injury_vlk --database data/database/project2.db
```

Команда перевіряє попередню схему/guards, integrity/FK та дублікати, бере maintenance lease, створює приватний SQLite backup `*.before-injury-vlk-…sqlite3`, додає лише індекс у BEGIN IMMEDIATE. Є rollback DDL та повторний no-op; невідомий індекс під тим самим ім’ям не замінюється. Колонки/дані/старі завдання не переписуються, автоматичної міграції або backfill немає. Нові БД відразу мають індекс. Для вже збережених поранень завдання створиться при наступному збереженні поранення/пов’язаної ВЛК/нагородження; просте читання не змінює кадрові записи. Робочу БД під час реалізації не мігрували й не скидали.

Вільний доступ/ролі/авторизація не змінені. Чинні документи, нагородження та атомарність їхніх операцій збережено. Нові перевірки — tests/test_injury_vlk.py та tests/browser/injury_vlk.cjs.

## Узгоджений процес ВЛК і контроль окремих проходжень

Цей розділ уточнює попередні правила: наявність будь-якого старого завершеного ВЛК більше не закриває нове проходження за тим самим пораненням.

### Стани, підстави та незалежні дати

Стани: NEEDS_EXAM «ВЛК потребує», PLANNED «ВЛК заплановано», COMPLETED «ВЛК пройдено», INTERRUPTED «ВЛК перервано». Створюються тільки перші три. INTERRUPTED дозволено при редагуванні PLANNED; надалі можна виправляти реквізити цього перерваного запису, але не переводити його в інший стан. Для наступного проходження створюють новий запис і нове направлення. Копіювання старих реквізитів/копій автоматично не виконується; використання того самого документа в категорії referral для іншого ВЛК відхиляється.

| Поле | Семантика |
| --- | --- |
| planned_on | Дата початку ВЛК. Збережено стару колонку й усі її значення; перейменовано лише підпис форми. |
| ended_on | Незалежна дата завершення проходження, нова nullable Date. |
| issued_on | Дата видачі довідки; не прирівнюється до завершення. |
| interrupted_on / interruption_reason | Точна дата й причина переривання, тільки INTERRUPTED. |

Відсутні компоненти/значення не вигадуються. Перевіряються календар і послідовність: початок ≤ завершення ≤ видача, коли обидві відповідні дати відомі; переривання ≥ початок. Перерваний запис не має дати завершення або результату придатності. Немає порівняння з «сьогодні», тому дозволені погоджені майбутні чи історичні предметні дати.

NEEDS_EXAM потребує хоча б однієї підстави: injury_id, basis_note або пов’язаного документа-підстави (recommendation/referral/discharge/other). PLANNED також зберігає підставу й обов’язково має planned_on. COMPLETED потребує рівно трьох обов’язкових реквізитів: issued_on, number, fitness; установа/діагноз/дати проходження необов’язкові. INTERRUPTED потребує початку, дати та причини переривання. Поля інших погоджених реквізитів не видалені.

Під час створення/редагування можна передати необов’язковий basis_document_id верхнього рівня в POST /medical/exams[/id]. Це існуючий PersonDocument тієї самої особи; посилання категорії other створюється разом із ВЛК/аудитом/завданням у тій самій транзакції. У GUI є поле ID документа-підстави. Для користувача без готового документа достатній опис підстави; після створення копії й направлення додаються чинним предметним інтерфейсом. Нові фіктивні документи чи направлення не генеруються. Наявність електронної копії не є новою умовою планування.

Старі неповні COMPLETED не виправляються, не видаляються й не змінюють статус під час читання/міграції. Вони залишаються доступними для активного вибору за чинним правилом. Для редагування потрібні всі три обов’язкові реквізити. active_exam_selection/MedicalSelection не замінені: лише COMPLETED, однозначна остання дата або ручний пріоритет. Нове незавершене ВЛК не скидає поточну довідку.

FIT_SUPPORT — той самий код БД. FITNESS та fitness_label(code) дають «Обмежено придатний» для інтерфейсу/таблиць; FITNESS_OFFICIAL та fitness_label(code, official=True) дають «Придатний до служби в тилових частинах забезпечення» для майбутніх офіційних документів. Генерацію Word/рапортів цей етап не додає.

### Контроль конкретного проходження

PersonnelTask отримав nullable exam_id → MedicalExam та унікальний partial index one_exam_control_task: максимум один нескасований injury_vlk/exam_vlk на конкретний запис ВЛК. Owner-guard перевіряє ту саму особу. Факти ВЛК, завдання, передача контролю та аудит синхронізуються в одній service_transaction(immediate=True).

- injury_vlk спочатку очікує рішення без MedicalExam, як і раніше. Перше пов’язане проходження прив’язується до цього процесу; без дублювання відкритого контролю.
- Наступне окреме проходження або ВЛК без поранення отримує власне exam_vlk. Старий завершений запис не закриває його.
- NEEDS_EXAM/PLANNED/INTERRUPTED залишають свій контроль OPEN; тільки COMPLETED закриває контроль цього exam_id. Повторне збереження не дублює завдання.
- Зміна injury_id перераховує обидва поранення. Якщо вже створений окремий контроль передається відкритому injury_vlk, старе завдання позначається CANCELLED із причиною передачі, зберігає exam_id/історію, а нове стає єдиним активним контролем. FK не підбираються за текстом.
- Явне «ВЛК не потрібна» з причиною зберігає пріоритет і не переписується автоматикою. Водночас реально наявне незавершене проходження має окремий відкритий контроль; рішення щодо поранення не підміняє факт його завершення.
- Перерваний запис і його невирішений контроль лишаються в історії/відкритих питаннях. Нове направлення — інший запис і контроль; завершення нового не переписує перерваний старий.

Створення/підтвердження нагороджень та injury_award не змінені. Універсальне редагування контрольних завдань не дозволяє довільно підміняти автоматичний статус/джерело; відповідальні відомості й примітку можна уточнювати.

### Редактор і картки

`+ Новий запис` відкриває чистий редактор. Вибраний стан керує видимістю та обов’язковістю полів; INTERRUPTED недоступний у новому записі, доступний лише для запланованого/вже перерваного при редагуванні. Після успіху список оновлюється, поля/ID/revision очищуються, редактор згортається, вкладка ВЛК лишається активною, показується Bootstrap Toast «Запис створено» / «Зміни збережено». Помилка сервера зберігає чернетку.

Картки ВЛК — нативні details/summary, початково згорнуті. Summary містить номер/стан, відомі дати початку/завершення/переривання, номер довідки, компактну придатність та «Актуальне ВЛК»; порожні значення — «—». Усередині — реквізити, підстави, документи, зв’язки й редагування. Незавершені (включно з INTERRUPTED) показуються перед завершеними; всередині — спадання відомої дати переривання/завершення/видачі/початку та стабільний ID як tie-breaker. За відсутності завершених відображається «Актуальне ВЛК не визначено».

### Міграція процесу

Для наявної медичної БД після зупинки сервера/SQLite-клієнтів виконайте **замість повторного запуску старих медичних міграцій**:

```sh
python -m app.database.migrate_vlk_workflow --database data/database/project2.db
```

Міграція перевіряє попередні колонки/guards, integrity/FK, бере maintenance lease й SQLite backup `*.before-vlk-workflow-…sqlite3` з 0600. Три nullable колонки додаються в копії person_medical_exams, а nullable exam_id — до personnel_tasks. Через CHECK трьох старих статусів SQLite потребує транзакційного перенесення лише person_medical_exams: усі ID, старі значення, revision та зв’язки копіюються без вигаданих реквізитів. Довідки, ручний вибір, документи/файли та аудит не переносяться в нові сутності. Оновлюються медичні guards та індекси; інші тригери й додаткові індекси ВЛК збережені. FK вимкнені лише на технічному connection під час перебудови; до commit виконується foreign_key_check, потім FK знову ввімкнені. DDL має rollback; часткова/невідома схема відхиляється. Повторний запуск актуальної схеми — no-op. Нові БД відразу мають нову схему.

Міграція не прив’язує старі завдання до довільних ВЛК й не змінює їхні статуси. Прив’язування/синхронізація відбудеться при наступному збереженні медичних фактів через сервіс; читання зберігає старі записи. Приватні файли не переміщуються. Робочу БД під час реалізації не мігрували/не скидали. Користувачі, ролі й чинний вільний режим доступу незмінні.
