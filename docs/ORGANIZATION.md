# Організаційна структура та незалежні версії штаток — етап 1

Реалізація у `feature/security` поверх Security 1.3. Цільова БД — PostgreSQL 17; Alembic head — `0008_organization`. Робоча БД не мігрується під час запуску застосунку. Старі призначення залишаються єдиними `PersonAssignment`, без таблиці поточного стану.

## Дані та межі відповідальності

| Файл / сутності | Призначення |
| --- | --- |
| `models/organization.py`: `OrgUnit`, `OrgUnitState` | Незмінний ID підрозділу, явний вид, період існування; датовані назва й один основний батько. |
| `OperationalSubordination` | Окремі датовані оперативні зв’язки, у тому числі кілька одночасних; основне підпорядкування не змінюють. |
| `OrgAudit` | Незмінюваний журнал із реальним User, UTC, операцією, before/after та причиною. |
| `models/organization_staff.py`: `OrgCoverage` | Однозначне джерело штатки для конкретного org_unit_id на включеному періоді. |
| `OrgStaffImport`, `OrgStaffImportRow` | Квитанція, незмінний preview, результати рядків, знімки реквізитів, revision і відомості про відкликання. |
| `OrgReassignment` | Потреба опрацювати анульоване помилкове призначення: FK старого запису, рекомендованої посади й нового підтвердженого запису. Не кадровий стан. |

Router → Service → Repository → SQLAlchemy збережено. `organization.py` відповідає за дерево, `organization_staff.py` — за джерела/зіставлення/перепризначення, `organization_import.py` — за підтвердження й відкликання. `organization_excel.py` лише читає та перевіряє книгу. Репозиторії не виконують commit. Чинні Person Picker, ProfileDates, авторизація, CSRF, захист preview і StaffService повторно використані.

## Дерево на дату

Види: `unit`, `regiment`, `battalion`, `company`, `platoon`, `squad`, `other`. Глибина не визначає вид і не обмежена фіксованими рівнями. Можна почати з кореня, пізніше створити батька й окремо встановити основне підпорядкування з фактичної дати. Попередній період зберігається. Порожні підрозділи дозволені.

Назви порівнюються за NFC, згорнутими пробілами й регістронезалежним ключем. Однакові назви дозволені під різними батьками або в непересічних періодах; одночасні дублікати серед коренів теж заборонені. Перевіряються історичні цикли, перетини й існування батьків у всьому періоді, а не лише сьогодні.

Розформування завершує фактичне існування з датою. Анулювання позначає помилковий запис, потребує причини та аудиту. Залежні штатні джерела, посади, основні й оперативні зв’язки треба опрацювати явно. Фізичного видалення немає. Нове формування отримує новий ID.

У `/admin/organization` доступні дата перегляду, дерево, історія, створення, перейменування, окрема зміна батька, оперативні зв’язки та їх завершення, розформування/анулювання. Drag & Drop та стрілки змінюють **лише порядок сусідів** з перевіркою revision. Переміщення під іншого батька й прив’язка посади — окремі форми та service actions.

## Однозначне джерело штатки

Незалежну StaffStructure має лише `company`, `battalion`, `regiment` або `unit`, незалежно від глибини дерева. Для вибраного взводу/відділення береться найближчий такий предок. Не створюються версії взводів або відділень.

Приклад: з 01.06.2026 змінюється 3 взвод 2 роти. Створюється **повний ротний знімок** із новими Position ID, включно з незміненими посадами інших взводів. Батальйонна StaffVersion, її реквізити й історичні Position залишаються. Для кожного org_unit_id роти попереднє покриття закінчується 31.05.2026, нове починається 01.06.2026. Покриття решти батальйону не змінюється.

Вибір чинної посади враховує її період, стан анулювання, життя підрозділу та **точний** OrgCoverage для пари підрозділ/версія. Глибина предка або останній час створення не визначають джерело. Після завершення/відкликання джерела старий батьківський штат самостійно не відновлюється. Новий дочірній підрозділ не успадковує джерело неявно: покриття створюється під час підтвердженого імпорту його посад.

Погоджена кадрова політика: призначення у заміненій області треба **явно завершити до першого дня нової версії**, потім окремо призначити людей. Імпорт не завершує, не переносить і не створює призначень. Нові офіційні версії вакантні. Перевірка відмовляє навіть при одному незавершеному призначенні; весь імпорт відкочується.

У `/person-positions` типовий вибір після запровадження покриття — сукупний чинний штат усіх джерел на `as_of`. Явний `version_id` збережений. Колонки, пресети, копіювання, фільтри, сортування, Міражі та Undo/Redo використовують чинні компоненти. Спільний effective-предикат підключено до таблиці, official picker та `assignments_at`; журнал подій не отримує дубльованого складу.

## Контрольоване зіставлення старих даних

Міграція залишає `StaffStructure.org_unit_id` і `Position.org_unit_id` старих записів NULL. Текст `unit_short` не використовується для здогадок.

1. Створити дерево з правильними фактичними датами.
2. У `/admin/organization/staff?unit_id=ID&on=YYYY-MM-DD` явно зіставити стару структуру з власником рівня роти або вище.
3. Вибрати її версію й явно вказати підрозділ кожної старої посади; за потреби окремо вказати керований підрозділ.
4. Перевірити джерела на дату та склад штатки. Створюється покриття старої версії, призначення й накази не переписуються.

До зіставлення старі версії працюють у перехідному режимі. Новий scoped-імпорт відмовляє, якщо на його дату є чинна legacy-структура з невідомим організаційним власником; також не допускає незіставлених посад вихідної структури. Це усуває ризик одночасного показу невідомого старого джерела й незалежної заміни. Спочатку потрібне явне рішення користувача.

Установлений `Position.org_unit_id` і власник StaffStructure незмінні. Для іншої належності потрібна нова офіційна версія з новими Position ID. Помилковий керівний `managed_unit_id` можна виправити окремим підтвердженим зіставленням із причиною, revision та аудитом; це не зміна належності посади. Старий `/admin/staff` залишається для перегляду/виправлення legacy-даних; щойно встановлено організаційне покриття, старий імпортер відмовляє у створенні нових непов’язаних посад. Нові імпорти виконуються з вибраного підрозділу.

## Excel

Завантажуваний шаблон: `/admin/organization/staff/template?depth=3`; `depth` задає кількість `child_N`. Використовується тільки аркуш `positions`.

- Рядок 1: `parent`, `child_1`, `child_2` … `child_N`, `position_number`, `code`, `unit_short`, `name_short`, `name_nominative`, `name_genitive`, `name_dative`, `name_accusative`, `name_instrumental`, `name_locative`, `name_vocative`.
- Рядок 2: пояснення; не обробляється як дані.
- Від рядка 3: шлях і чинні 11 реквізитів посади. Число дочірніх колонок довільне; пропуски рівня в заголовках/усередині шляху відхиляються.
- `parent` має відповідати назві **вибраного ID** на дату імпорту. Дочірні частини зіставляються лише серед дітей відповідного батька, не глобальним пошуком назв.
- Відсутній дочірній шлях створюється лише за підтвердженими рядками як `other`; вид не вгадується за текстом. За потреби рівні з явними видами треба створити в дереві заздалегідь.
- Межі: 5 МБ файлу, 50 МБ розпакованого XLSX; збережено перевірки архіву, структури, заголовків і даних посад. Помилки містять фактичний номер рядка Excel. Інші аркуші ігноруються.

Відсутність шляху або посади у книзі не означає вилучення чи розформування. Новий шаблон не замінює старий `reference_data.xlsx` для legacy-засівання.

## Режими й квитанції

| Режим | Підтверджена дія |
| --- | --- |
| Доповнення (`add`) | Нові посади у чинне однозначне джерело; однакові дані не дублюються. Зайнятий номер з іншими реквізитами залишається конфліктом. |
| Нова офіційна версія (`official`) | Повний знімок власника рівня роти або вище, нові Position ID, вакантні посади. Невибрані/відсутні рядки копіюються з джерела без зміни. Вилучення — лише за явно вибраними ID та підтвердженням. |
| Точкове виправлення (`correct`) | Відмінності реквізитів конкретної посади, причина й підтвердження; Position та правильні assignment_id зберігаються. |
| Повна заміна помилкової області (`replace`) | Явно вибрані помилкові Position і їхні призначення логічно анулюються; створюються правильні посади та потреби перепризначення. Решта області зберігається. |

Preview показує шлях, джерела копіювання, ID/реквізити посад, відмінності, людей/періоди залежностей, попередження й конфлікти. Якщо джерело явно закрито напередодні, official preview показує цю попередню дату копіювання. Квитанція зберігає всі рядки; можна підтверджувати лише безконфліктні або зберегти конфлікти без кадрових змін. Подальше опрацювання доступне після reload через список квитанцій.

Конфлікт можна явно пропустити зі збереженням поточного запису або виправити реквізити тієї самої посади з причиною та revision. Структурні помилки/неоднозначний шлях потребують нового preview. Повторний POST тієї самої квитанції не дублює рядки. Нова книга з тим самим номером не перезаписує дані сама. Якщо знімок об’єднує незалежні джерела з однаковими номерами, потрібне явне узгодження номерів/вилучення: у новій фізичній версії номери залишаються унікальними.

Перед підтвердженням повторно перевіряються дерево, вихідні й уже створені посади, created-підрозділи та revision. Перед помилковою заміною окремо перевіряється, що показаний склад залежних призначень не змінився. Пізня зміна шляху вже скопійованої вакантної посади створює інший Position ID; попередній порожній знімок логічно анулюється, його належність не переписується. Посада з будь-якою історією призначень так не змінюється.

Список «Потребують перепризначення» містить старий запис, людину, фактичні дати й накази, рекомендовану нову посаду. Користувач перевіряє й підтверджує ці дані. Створюється звичайне призначення з чинними перевірками, а не фіктивне переведення. Початкові записи й їх аудит залишаються.

Відкликання потребує причини та підтвердження. Перевіряються всі наступні призначення, revision, залежні квитанції/джерела/посади. Після дозволеної операції створені посади/покриття, а для official і порожня створена версія, логічно анулюються; точкові реквізити компенсуються за знімком. Квитанції, рядки, порожні створені підрозділи та історія зберігаються. Призначення й попереднє джерело автоматично не відновлюються. Анульована версія не блокує інший період, але її назва лишається історично зайнятою.

## Транзакції та доступ

`organization_write` повторно використовує `StaffService.write_unit`: одна транзакція даних та аудиту, відмова за незбережених сторонніх змін, PostgreSQL advisory xact lock поточної схеми **до** row locks, revision; SQLite — `BEGIN IMMEDIATE`. Увесь staffing/organization write path бере той самий schema-scoped lock, щоб зміна джерела й конкурентне призначення не утворили некоректну пару. Це навмисно серіалізує кадрові записи в межах схеми; звичайне читання не блокується.

PostgreSQL перевіряє історичне дерево відкладеними тригерами, періоди — EXCLUDE, незмінність ID/належності й аудит — guard-тригерами. Організаційні й staffing записи фізично не видаляються. Помилка вставки аудиту відкочує також кадрові зміни. Анульовані Position не блокують номер нової виправленої посади; активний номер у версії унікальний.

Маршрути `/admin/organization` і `/admin/organization/staff` використовують чинну персональну MFA-сесію Master/Admin, CSRF та Origin-перевірки. Actor береться із сесії; клієнтський actor_id ігнорується. Preview прив’язаний до конкретної адміністративної сесії й ресурсу `organization-staff`. Окремі service actions `reorder`, `reparent`, `bind`, `import` тощо підготовлені для майбутнього ACL, але зараз перевіряють лише чинні ролі Master/Admin. Матриця ACL, права за посадою й Security 1.4 не реалізовані.

## Міграція та перевірки

`0008_organization` після `0007_mfa_sessions` додає вісім таблиць, nullable організаційні FK, періоди/анулювання Position, метадані анулювання StaffVersion, індекси й заморожені SQL guards. Старі користувачі, записи, дати, накази й audit збережені; немає автоматичного зіставлення, анулювання чи вигаданих минулих операцій. Старі ревізії не редагуються. Downgrade відмовляє у видаленні історії; відновлення — з перевіреного backup в окрему БД.

Після backup, перевірки цільового `DATABASE_URL` та зупинки сервера адміністратор окремо виконує:

```powershell
python -m alembic current
python -m alembic upgrade 0008_organization
python -c "from app.database.db import engine; from app.database.postgresql import require_postgresql_schema; require_postgresql_schema(engine)"
```

У цьому завданні міграція виконувалася **тільки в ізольованих схемах project2_ci**. Development/production не змінювалися, reset не запускався. Команди резервування — [POSTGRESQL_SETUP.md](POSTGRESQL_SETUP.md).

Автотести: `tests/test_organization*.py`, `test_admin_organization*.py`, `tests/postgresql/test_organization_tree.py`, `test_organization_staff.py`; Chromium `COLUMN_STAGE=organization` та `organization_staff`. Підсумкові фактичні результати — у [CURRENT_STATE.md](CURRENT_STATE.md). PostgreSQL concurrency перевірено окремими підключеннями; SQLite/browser — синтетичні дані й тимчасові файли. Повного browser CRUD на PostgreSQL та ручного випробування великих реальних штаток немає.
